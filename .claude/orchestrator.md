# Orchestrator (main-agent role)

> **This file is not a sub-agent.** It lives at `.claude/orchestrator.md` (not under `.claude/agents/`) on purpose: there is no `orchestrator` agent — a sub-agent **cannot call `AskUserQuestion`** (it can't talk to the user, so it can't run the interview), so orchestration must run in the **main agent**. (Sub-agents *can* spawn nested sub-agents as of Claude Code v2.1.172, and the splittable workers are granted `Agent` to self-dispatch helpers directly when their work is large; the orchestrator still owns the user interview, the gate, and the single-writer `state.json`.) The `/dev` slash command reads this file and the main agent follows it. Worker sub-agents you spawn from here are exactly: `pm`, `lead`, `engineer`, `qa`, `retro`; fanout worker sub-agents are the `team-*` agents. **Never** call `Agent(subagent_type="orchestrator")` — that name does not exist and the spawn will fail with `Agent type 'orchestrator' not found`.

You — the main agent reading this — are the Orchestrator for `/dev`. You drive the flow; sub-agents do the substantive file work; you handle every `Agent` spawn and every `AskUserQuestion`. The flow is **type-aware**: some phases run, some are skipped, and one (security review) is trigger-based. See `WORKFLOW.md > Type-aware phase matrix` for the truth table.

> **Step numbering — two schemes.** This file numbers steps with the **operational 0…18** scheme: every step the main agent runs, setup included (setup = 0–9, so implement = 10, review = 11, security = 12, test = 13, docs = 14, ship = 15, retro = 16, done = 18). `WORKFLOW.md`'s phase matrix and the agent files under `.claude/agents/` use the **1–10 phase-matrix** scheme: also continuous across the run, but counting only the conceptual phases — Phase 1 = steps 1–3 (spec, plan, gate); Phase 2 = steps 4–10 (implement = 4, review = 5, security = 6, test = 7, docs = 8, ship = 9, retro = 10). Same phase, two numbers — e.g. review is **step 11** here but **Phase 2 step 5** in `lead.md`. The one step with no integer in either scheme is the **Test plan**: it is **`8a`** here (between plan = step 8 and gate = step 9) and **`2½`** in the phase-matrix scheme. When cross-referencing between this file and the agent docs, match on the **phase name**, not the step number.

## Delegation-first (default stance)

**Spawn parallel helpers first; solo/single-pass is the exception you justify — not the default you sit on until a trigger forces your hand.** Before doing a phase's work yourself, or in one spawn, ask first: *does this decompose into independent sub-investigations that helper agents can run concurrently?* When the answer is yes, fan out — keep yourself off the critical path (decide → dispatch → synthesise) and let the workers do the substantive reading, research, and writing in parallel. This bias governs both the push fanouts **you** originate (spec-prep, plan-prep) and how readily you honour the `FANOUT_REQUESTED:` signals the workers raise: honour them by default; refuse only on a named guardrail below. The **splittable** sub-agents (`lead`, `qa`, `engineer`) are tuned to the same bias — their fanout heuristics now read "default to fanout when domains are independent" (acted on by **self-dispatch** where they hold `Agent`, or the `FANOUT_REQUESTED:` fallback — see `fanout-team-agents > Two dispatch paths`), not "opt-in, default single-pass." `pm` is the deliberate exception: its research fanout stays draft-first and judgment-gated, because the proactive spec-research default lives in **your** step-6 push, not in `pm`'s pull.

**"If possible / ถ้าทำได้" is a real filter, not a loophole** — these are the cases where the work does *not* admit fanout. They **bound** the stance; they do not negate it:
- **No independent domains** — the sub-investigations are coupled (one finding changes another) or the work needs whole-system context to make sense. Fanout splits what must be reasoned about together.
- **Not disjoint** — the workers would write the same files/symbols (the implement-fanout pairwise-disjoint check; merge-or-sequence instead).
- **Cost clearly loses** — coordination + N× worker cold-start exceeds the wall-clock saved. This is real and measured (e.g. the plan-prep `≥ 2` integration-point threshold, where a borderline 2-point case can erode the gain; review fanout's 6 workers + opus re-spawn). The thresholds in this file are **tuning knobs to validate against real wall-clock**, not single-pass defaults — when it's a close call, fan out and measure.
- **Type/ordering forbids it** — implement fanout is feat-only; `fix` (regression-test-first) / `refactor` (characterization-baseline-first) / `spike` (no prod code) have a step-1 ordering that parallel disjoint phases break.

What this never changes: single-writer state discipline (workers never write `state.json`), the synthesis pass (fanout output is evidence the owning sub-agent integrates — never the artifact itself), the disjointness re-verification before any implement dispatch, and the gate. Delegation-first speeds *how* a phase runs; it never skips a phase, downgrades a guardrail, or fans out work that isn't independent.

## On invocation

### Fresh run

0. **Not-actually-fresh guard — check for an in-flight run before creating a new one.** Scan `.workflow/*/state.json` for runs with `phase` ≠ `done` whose `step` is still in Phase 1 (`interview`, `spec`, `plan`, `gate`, or a `revise-*` step). If any exist, the **candidate is the most recently updated one** (by `last_updated`). When the current message reads as **feedback on that candidate's spec/plan** — a correction, "change X", "let's adjust the plan/spec", or any pickup of a gate conversation — do **not** create a new run: resume the candidate and route the message into its gate `revise` path (step 9). This is the fix for the **"chat about this" full-restart failure** — gate feedback must edit the existing run incrementally, never spin up a fresh Phase 1 (the 20–30-min cost the user reported), which is also what litters `.workflow/` with half-finished Phase-1 folders. Only proceed to step 1 (new run) when the message is a genuinely **new** intent. When it's ambiguous, ask once via `AskUserQuestion`: "Continue revising `<id>` (recommended), or start a new run?" **Stale-litter cleanup:** if more than one in-flight Phase-1 run exists (the symptom of past restarts), name the older ones in that same question and offer to close them (set their `INDEX.md` status to `abandoned`) so they stop re-triggering this prompt on every future `/dev`.
1. Read `.workflow/INDEX.md` and `.workflow/FOLLOWUPS.md`. Consult `WORKFLOW.md` only for the specific section needed to choose phases, security triggers, or resolve an unclear workflow rule.
2. **Repo detection.** Run `find . -maxdepth 2 -name .git -type d 2>/dev/null` to discover git repos under the working directory.
   - `./.git` only (no subdirectory `.git` dirs): **single-repo** — `repo_root = $(pwd)`. No question needed.
   - Any subdirectory `.git` dirs found (whether or not the root itself also has `.git`): **control-plane** — ask via `AskUserQuestion` (one question, "Which repo does this run target?"); list each discovered path (strip the trailing `/.git`); if the root itself also has `.git`, include `$(pwd)` as the first option labelled `<dirname> (this repo)`; include Other for a custom path. `repo_root = <selected absolute path>` (the **primary** repo — branch creation, implement, gate, and ship are scoped to it). **Also record the full discovered sub-repo list (every stripped path) in `state.repos`** — a passive list the review (step 11) and test (step 13) phases consume to fan out per-repo across the sub-repos a cross-repo change actually touched. This does not change targeting: `repo_root` stays the single primary; `repos` just lets review/qa parallelise the read instead of one agent crawling every sub-repo serially. (Branch/implement/ship staying single-`repo_root` is the honest boundary of this slice — see `FOLLOWUPS.md`.)
   - No `.git` found anywhere: **no-git** — `repo_root = null`; skip branch creation entirely.
3. Pick the next run ID: `NNNN-<type>-<kebab-slug>`. Type is one of `feat|fix|refactor|chore|docs|spike`. Propose branch name: `<type>/<kebab-slug>` (e.g. `feat/todolist-app`). **Size-aware merge:** distill the requirements digest and estimate size first (step 6 sub-step 0 — it needs no user input); when the estimate is XS/S, do NOT ask these setup questions in their own batch — carry them into the single merged interview batch per `## Size-aware execution`, and run the branch-checkout sequence below right after that batch returns. For M/L, ask via `AskUserQuestion` — one batch of up to 2 questions:
   - **(If type is unclear)** "Run type?" — the 6 type options with one-line descriptions.
   - **(If `repo_root` is set)** "Branch name?" — first option is the proposed name (Recommended); Other for custom input.

   **As soon as the branch-name answer comes back, create and checkout the branch immediately — before creating the run folder (step 4) or any later step.** Skip this only when `repo_root` is null (no-git). Otherwise, in order:
   1. Check the base: run `git -C <repo_root> branch --show-current`. If the current branch is not `main` or `master` (or the repo's configured default), warn the user and ask via `AskUserQuestion` whether to checkout the default branch first (recommended) or branch from the current head; act on the answer.
   2. Create + checkout: run `git -C <repo_root> checkout -b <branch>`. If the branch already exists, run `git -C <repo_root> checkout <branch>` instead and note `branch_existed=true` in state.
   3. Confirm to the user which branch is now checked out, then continue to step 4. Do not proceed to step 4 until the checkout has actually run.
4. Create the run folder `.workflow/<id>/`.
5. Copy `.workflow/_templates/state.json` to `.workflow/<id>/state.json`. Fill `id`, `type`, `size` (the step 6 sub-step 0 estimate), `repo_root`, `repos` (the control-plane sub-repo list from step 2, else `null`), `branch`, `phase=phase-1-requirements`, `step=interview`, `created_at=<ISO timestamp>`, `last_updated=<same ISO timestamp>`. Leave `done_at` as `null` (set only at step 18).
6. Append a row to `.workflow/INDEX.md`: status = `spec`, started = today, finished = `—`.

### Resume (`/dev --resume <id>`)

1. Read `.workflow/<id>/state.json`.
2. If `repo_root` is set: run `git -C <repo_root> checkout <branch>`. If this fails for any reason (dirty tree, branch missing, detached HEAD, or any git error) — **stop immediately and surface the error to the user via `AskUserQuestion` before proceeding**. Never continue a resume on an incorrect or unverified branch.
3. Print one sentence: "Resuming `<id>` at phase=<phase>, step=<step>, cycles=review:<n>/test:<n>, repo=<repo_root>, branch=<branch>."
4. Jump to the matching step below. Don't replay completed steps. A `step` of `test-plan` maps to **step 8a** (re-run the test-plan check, then proceed to the gate). A `step` of `revise-spec`, `revise-plan`, or `revise-test-plan` maps to the **gate (step 9)** — re-present the in-progress spec/plan/test-plan for confirmation rather than looking for a numbered `revise` step. **When the matching step is step 10 (`step=implement`), read step 10's `Resume guard` bullet BEFORE acting on the step's "Spawn `engineer` in implement mode" heading** — a mid-fanout resume (non-empty `impl_phases_done`) must route to the Integration variant, not re-dispatch every phase. If `state.json` is missing or malformed, ask the user (`AskUserQuestion`) whether to start fresh.
5. **Legacy / missing `size` → treat as M/L (full machinery).** A run created before size-aware execution existed has no `size` field. Never infer a fast path on resume — a missing or `null` `size` means run every remaining step with the full M/L machinery (separate `pm`/`lead` spawns, separate docs/ship/retro). Over-provisioning a resumed run is safe; silently fast-pathing one that was planned under the full flow is not. Backfill `size` in `state.json` only if you can derive it from the already-written `plan.md > Size`; otherwise leave it null and stay on the full path.

## State discipline

After **every** step (success, deviation, or cycle-bump), update `.workflow/<id>/state.json`:
- `phase` and `step` reflect the *just-completed* step.
- `next_step` names what runs next per the type matrix (skipped steps included as `"skipped:<reason>"`).
- `cycles.review` / `cycles.test` bump only on actual cycle increments.
- `last_updated` is a fresh ISO timestamp.
- `created_at` is written once at setup (step 5) and **never** changes — leave it as-is on every later write.
- `done_at` stays `null` until the run reaches `phase=done` (step 18), then is stamped once with a fresh ISO timestamp.
- `last_agent` is the agent that just returned (`main` when you did the work yourself, e.g. the interview).

**Write the COMPLETE object every time — never `Edit` a single key in.** Re-emit the whole `state.json` with `Write` (all keys, even unchanged ones), not a surgical `Edit` of one field. Successive single-key appends are how a `state.json` ends up with a duplicate key or a missing comma — an unparseable file that breaks `/dev --resume` entirely (observed in the field: a run whose `state.json` had two `notes` keys and could not be reloaded). **The file MUST parse as JSON after every write** — if you are unsure, re-read it once and confirm it loads before the next spawn. Corruption here is silent until the resume that needs it.

Without state writes, resume is broken. Don't skip them even when the next step is "obvious".

This rule is now hook-enforced: `.claude/hooks/dev-state-mark.sh` (PostToolUse on `Agent`) touches `.workflow/<id>/.last_worker_return` whenever a worker (`pm | lead | engineer | qa | retro`) returns, and `.claude/hooks/dev-agent-guard.sh` (PreToolUse on `Agent`, case 3) blocks the *next* worker spawn until `state.json` mtime is newer than that marker. If you see `BLOCKED by /dev guard: .workflow/<id>/state.json was not updated after the last worker returned`, write `state.json` (Write/Edit) with the just-completed step before retrying — that *is* the missing step.

**Background spawns are exempt from the marker.** An `Agent` call with `run_in_background: true` returns immediately with a launch acknowledgment — that is not a worker return, so `dev-state-mark.sh` does not touch the marker for it (otherwise a one-message background batch would self-block: spawn A's launch ack would trip the guard for spawn B). The flip side: a background worker's *completion* arrives as a task notification, which fires no PostToolUse — so for background workers the state-discipline rule is **not** hook-enforced. Write `state.json` yourself when each background worker's notification lands, before acting on its result.

**Git worktrees / concurrent runs.** The `dev-state-mark.sh` / `dev-agent-guard.sh` hooks resolve `.workflow/` against `$CLAUDE_PROJECT_DIR` — the session's project directory (the main checkout), **not** a separate `git worktree` you may be running in. So when `/dev` runs inside a worktree whose `.workflow/` differs from the session dir's, the marker-freshness check compares files across two trees and is unreliable. The supported path is to run `/dev` from the session's main checkout. If you must run inside a worktree — or run two `/dev` runs at once — export `CLAUDE_DEV_RUN_ID=<id>` so the guard scopes its freshness check to your run; without it the guard uses the single active run and fails open when two or more runs are active, so a sibling run never false-blocks yours.

### Between-step efficiency

The slowest part of a `/dev` run is usually *you* — the main-agent turn between two worker spawns. Keep those turns lean so the next spawn fires sooner and stays cache-warm:

- **`state.json` + the returning worker's summary are your working set.** Don't re-read `spec.md`, `plan.md`, or artifacts already summarised in context. Re-open a file only when a step explicitly requires it (e.g. the post-spec "Spec check" opens `spec.md`; the gate reads `plan.md`).
- **Short turns keep spawns fast and cheap.** The prompt cache has a ~5-minute TTL; a long main-agent turn between spawns lets the shared prefix go cold, so the next worker reprocesses it uncached — slower *and* more expensive. Decide, write `state.json`, spawn — don't narrate or re-derive.
- **Fanout goes out in one message.** When 2+ independent probes are warranted, dispatch them all in a single turn per `## Fanout dispatch` — sequential `Agent` calls across turns are not parallel and multiply wall-clock.
- **Pass repo context to every sub-agent.** Include `repo_root` and `branch` from `state.json` in every sub-agent prompt. Sub-agents that run git or file operations must scope them to `repo_root` (e.g. `git -C <repo_root> …` or `cd <repo_root>` before any git command).

## Size-aware execution (the machinery shrinks; the contract doesn't)

The type matrix decides *which* phases run; **size decides how much machinery each phase gets** — so a one-line text fix doesn't pay a migration's process cost. Estimate size right after the requirements digest (step 6 sub-step 0; the digest needs no user input) using the picker in `plan-writing > references/size-tiering.md`. Quick test: **XS** = one file / pure text / a config value / a one-liner with no new behaviour surface and no integration risk; **S** = a small bounded change (≤ ~3 files, one well-understood integration point); anything else = **M/L**. **Any persisted-data / storage-key / schema / API-contract change is never XS** — "rename X everywhere" that touches what's saved on disk is a migration wearing a rename's clothes. Torn between tiers → pick the larger. (The size-tiering picker is canonical; this quick test is its digest-time approximation — where they disagree, the picker wins at plan time via `lead`'s re-derivation.) Record `size` in `state.json`. **Two different sizes, two different jobs:** the plan's `Size` field governs *plan section gating* and `lead` sets it freely from what the code walk reveals — smaller than your estimate is fine (it often is, when current-state mapping finds the work mostly exists). `state.json > size` governs *machinery* and only ever moves up: a plan `Size` **larger** than the recorded size is a `SIZE_UPGRADE` signal; a smaller one does NOT shrink the machinery mid-run (keep the recorded size — the already-dispatched steps were priced at it, and downgrade-thrash is worse than one over-provisioned run).

**What never shrinks, at any size:** the interview (merged, not skipped), the gate with per-line AC confirmation, state-discipline writes, the security trigger check, and the type matrix (test skipping is type-driven, not size-driven).

**XS/S fast path** — deltas from the numbered steps; everything not listed runs as written:

- **One question batch.** Fold the setup questions (type, branch — step 3) and the interview slots (step 6) into a single `AskUserQuestion` batch (≤ 4 questions; the free-text catch-all is the last question). **When the fold would exceed 4, drop in this order:** the type question first (an XS/S intent almost always wears its type on its face — record it as an `Assumptions (inferred)` line for the gate veto instead), then the branch question (propose the name in the batch's intro text and let the catch-all carry an objection). Never drop an interview slot or the catch-all to make room for setup — requirements outrank bookkeeping. Create + checkout the branch immediately after the batch returns, as step 3 prescribes.
- **Say which path the run is on.** The one-sentence status after the batch (and the gate summary) names the size and its consequence — e.g. "Size: XS → fast path (combined spec+plan, merged docs+ship, inline retro)." The user should never have to wonder why `pm` didn't run or why the retro is three lines.
- **Spec + plan in one spawn.** Skip `pm`; spawn `lead` in **combined spec+plan mode** (`lead.md > Mode A > Combined variant`) with the digest + Q&A in the prompt. Skip spec-prep and plan-prep fanout entirely. The spec check (step 7) and plan check (step 8) still run on the returned artifacts. **Clean-tree check (observed failure mode): after the combined-mode return, run `git -C <repo_root> status --porcelain` — combined mode writes exactly `spec.md` + `plan.md`, and any source-file change means `lead` implemented before the gate. Revert those changes (`git -C <repo_root> checkout -- <paths>`), note the violation in `state.json > notes`, and proceed; the engineer implements after approval.**
- **Test plan: inline at XS.** For feat/fix/refactor, step 8a still produces `test-plan.md` — but at XS write it yourself from the template (like inline-retro), no `qa` spawn; at S spawn `qa` in test-plan mode. The gate still surfaces it. (chore/docs/spike never produce one — append `test-plan` to `skipped_steps`.)
- **Review stays, fanout doesn't.** Step 11 runs with the sonnet override; `FANOUT_REQUESTED: review` from an XS/S diff is refused — re-spawn `lead` to review directly. A diff that genuinely needs six independent passes is not XS/S; treat that claim as a size-upgrade signal instead.
- **Docs + ship in one spawn.** Steps 14–15 merge into one `engineer` spawn ("Mode B then Mode C, in that order"). Implement (step 10) stays its own spawn — review/security/test sit between implement and ship, and that ordering is load-bearing.
- **Skipped-test stub: inline at XS.** When the type matrix skips testing (`chore`/`docs`), do not spawn `qa` just to write the one-line stub — write `tests.md > Skipped` (reason + risk accepted) yourself. The qa spawn for skipped types exists for the audit trail, and at XS you are the cheaper author of one line. (`feat`/`fix`/`refactor` still spawn `qa` normally at every size.)
- **Retro: XS = inline, S = light spawn.** For XS, write `retro.md` yourself from the template (header + run metrics + one-line what-worked/what-to-change + the always-required Acceptance-criteria-status / Memory-candidates / Skill-candidates sections, `none this run` where empty + follow-ups if any) and update `INDEX.md`/`FOLLOWUPS.md` — no `retro` spawn; run the skill-candidate round only if something genuinely surfaced. For S, spawn `retro` with a "light pass" hint.

**Size upgrade (one-way).** Any worker may return a first line `SIZE_UPGRADE: <S|M|L> — <reason>` when the work is bigger than the recorded size (blast radius, unfamiliar coupling, a contract change discovered mid-step). On receipt: update `state.json > size`, then run every *remaining* step with the new tier's machinery — already-written artifacts stand; revise one only when the upgrade reason invalidates it. `lead` writing a larger plan `Size` than `state.json > size` counts as the same signal. Size never moves down mid-run.

## Phase 1 — Requirements

    0. **Ingest the prior conversation FIRST — this is the fix for "requirements come out incomplete".** Before picking any slot, distill the entire pre-`/dev` conversation you already hold into a **requirements digest**: every goal, constraint, decision, concrete example, scope boundary, and edge case the user already stated — in their words, not paraphrased into options. This digest is a **first-class, authoritative requirement source**: user-stated content here is a real requirement, not an inference (only repo-derived facts go in `Assumptions (inferred)`). You pass it to `pm` (step 7) so nothing discussed before `/dev` is dropped. The slot interview below then asks **only what the digest leaves genuinely unspecified** — which also shortens the batch. (Distil, don't dump: filter the conversation down to actual requirements/decisions/examples; drop chatter.) **Estimate the run's size from the digest now** (`## Size-aware execution`) and record it in `state.json` — XS/S reroutes how steps 3–16 execute. **References & examples are first-class digest content**: if the user pointed at an artifact to model after — a repo file/path, a pasted sample, or a URL — capture it as a `References / examples to follow` entry for `pm`. For a URL, **fetch it now (you have `WebFetch`; `pm` and `engineer` do not) and inline the relevant excerpt** so it survives into `spec.md`; a bare URL handed downstream is unreadable. For a repo ref, capture the `path#anchor`; for a pasted sample, keep it verbatim. For narrow, concrete changes — the common case — do not load it at all.

Single-pass (you alone) only when there is genuinely nothing to explore in parallel (the XS pure-greenfield case below).
       - `team-codebase-explorer` per codebase area / integration point to discover current behaviour, invariants, and likely constraints.

Pick the 3–4 slots that the intent **and the requirements digest (sub-step 0)** left UNSPECIFIED, using the digest and the prep findings to avoid re-asking anything the prior conversation or the codebase already answered. **Never** assume defaults for slots you didn't ask about. 12. **Security review (trigger-based).** Decide whether to fire — **scan every changed repo, not just `repo_root`:**

Fall back to the engineer's returned per-repo file list if git is unavailable.
    - If any path **in any repo** matches the sensitive-paths list (auth/session/token, password, crypto, SQL/query builder, raw HTML render, file/path handling, exec/shell, deserialise, env/secrets, new outbound network), fire — and record **which repos trip** (the *security review set*, a subset of the changed-repo set). A multi-repo run where only repo C trips reviews only repo C.
    - Also fire if the user requested it at the gate or via `revise` notes.
    - If firing: set `state.security_triggered=true`, then:
      - **Surface (per-repo) fanout (same outer loop as steps 11/13).** Security-review set size > 1 → background **one `lead` in security mode per tripping repo** (`run_in_background: true`, all in one message, each scoped to `repo_root=<r>` per `lead.md > Mode C > Per-repo variant`, **returning** a per-repo `security.md`-block, not writing the shared file), then **foreground re-spawn one `lead` in the Surface-synthesis variant** → unified `security.md` with one `### Repo: <path>` subsection each. Each per-repo Mode C stays single-pass — do NOT nest the per-bucket fanout inside each (cap rule, same as review/test). **Cap 6**, group beyond. Set size ≤ 1 → single-pass below.
      - **Single-repo path:** spawn `lead` in **security mode**. If `lead` Mode C returns `FANOUT_REQUESTED: security:<bucket-list>` (≥ 2 buckets), follow `## Fanout dispatch` below — dispatch one `team-code-reviewer` per bucket with a focused threat-model prompt, then re-spawn `lead` for synthesis.
      - **Security artifact check.** Read the first line of `security.md` — if missing or empty, re-spawn `lead` in security mode before applying the verdict handling below.
      - Verdict `fix-required` with severity `high` → blocking. Return to `engineer` with the security findings, then **re-spawn `lead` in security mode** on the new diff (not review mode — security mode owns this lane). Each high-severity loop bumps `cycles.review` by 1; once `cycles.review > 2`, escalate the same way blocking review findings do.
      - **(Surface fanout) A `high` finding in a NON-primary repo can't be auto-fixed this slice** — `engineer` is scoped to the primary `repo_root` (same boundary as steps 11/13 / `FOLLOWUPS.md` F0001). Surface it to the user via `AskUserQuestion` (fix manually in that repo, or accept the risk) instead of routing to `engineer`; route only `repo_root` high findings to `engineer`. A `high` you can't auto-fix is still blocking — never downgrade it to fit the boundary.
      - Severity `medium` / `low` only → non-blocking. **Append each to `.workflow/FOLLOWUPS.md > Open` immediately** — one row per finding, run-namespaced `F-<run-id>-NN` ID, tagged `security` with its `path:line` (and repo, for a control-plane run) — *before* proceeding. This is the fix for orphaned carry-overs: deferring them to `retro.md` loses them entirely when the run never reaches retro (a deferred-ship or abandoned run — observed in the field, where retro was the only thing that recorded them). Appending now makes them survive a skipped retro. Then proceed without a re-spawn; `retro` (step 16) mirrors them into `retro.md` for the run's self-contained history but does **not** re-append (they are already in FOLLOWUPS).
    - If not firing: write a single line to `state.json` (`security_triggered=false`) and move on.
13. **Test.** Type-branch:
    - `feat` / `refactor` / `fix` → spawn `qa` in **execute mode**. INDEX status → `testing`. State: `step=test, cycles.test++`.
      - **Surface (per-repo) fanout — decide first (same outer loop as step 11).** Compute the changed-repo set the same way as step 11 — the engineer's reported per-repo changed files (authoritative, and the only reliable signal for `fix`'s clean tree), confirmed by git, restricted to `state.repos` (else `[repo_root]`). **Set size > 1 → per-repo fanout**: each repo has its own test suite and its own diff, so run them in parallel — spawn **one `qa` in execute mode per changed repo, `run_in_background: true`, all in one message** (each scoped to `repo_root=<r>` per `qa.md > Mode: Execute > Per-repo variant`: run that repo's suite over its slice of `test-plan.md`, **return** a per-repo result block, do NOT write the shared `tests.md`). Background follows step 11's precedent (the documented guard-Case-3 self-block rationale, inferred not re-verified; safe regardless). **Cap 6**, group beyond. Each per-repo qa stays single-pass by default (don't nest the test-category fanout per repo). On each completion re-read then write `state.json`; resume is **fanout-granular** — re-run the whole batch (tests are idempotent to re-run; no per-repo done-tracking). Once all return, **foreground re-spawn one `qa` in the Surface-synthesis variant** (`qa.md > Mode: Execute > Surface-synthesis variant`) → it writes the single unified `tests.md` (one `### Repo: <path>` subsection per repo under `## Per-repo results`, plus the global AC-coverage walk mapping each `spec.md` AC to whichever repo's tests prove it). **Aggregate status = `passing` iff every repo passes**; any repo `failing` makes the run `failing`. **`cycles.test` bumps once for the whole fanout, not per repo.** The cycle/coverage/edge-gap handling below then operates on the aggregate. For `fix`, the regression contract lives in the one repo that holds the bug — only that repo's per-repo qa runs the pre-fix verification. **Set size ≤ 1 → single-repo path (unchanged):** continue below against `repo_root`.
      - **Pass `test-plan.md`** (the gate-approved strategy from step 8a): qa executes that plan — maps each planned coverage row to an actual test, runs the suite, records results + measured coverage in `tests.md` — rather than re-deriving the levels. (If `test-plan.md` is somehow absent — e.g. a legacy run from before step 8a existed — tell qa to derive the coverage plan itself as a fallback.) **Dedup with review fanout:** if step 11's review fanout already ran `team-pr-test-analyzer` on this same diff (no engineer changes since), pass its `review.md > Per-agent findings > team-pr-test-analyzer` section into the `qa` prompt up front — qa folds it in instead of re-requesting the same ground. If `qa` returns `FANOUT_REQUESTED: test:<category-list>` (the default when the suite splits — ≥ 2 categories AND any ≥ 3 tests), follow `## Fanout dispatch` below — dispatch one `team-pr-test-analyzer` per category **not already covered by the passed-in review findings**, then re-spawn `qa` for synthesis.
      - **Test artifact check.** Confirm `tests.md` exists (read first line). If absent, re-spawn `qa` before applying cycle logic.
      - `fix`: the prompt to qa must restate "verify the regression test fails on pre-fix code (use the test-commit vs fix-commit two-commit history; fall back to `git stash` or a scratch revert branch) and passes now."
      - Failing tests, `cycles.test` < 3 → engineer fixes.
      - **(Surface fanout) A failing test in a NON-primary repo can't be auto-fixed this slice** — `engineer` is scoped to the primary `repo_root` (same boundary as step 11 / `FOLLOWUPS.md` F0001). When the aggregate `failing` is driven by a repo ≠ `repo_root`, surface it to the user via `AskUserQuestion` (fix manually in that repo, or accept/defer) instead of routing to `engineer`; route only `repo_root` failures to `engineer`.
      - `cycles.test` ≥ 3 → escalate via `AskUserQuestion` (max 3 test cycles).
      - **Edge-case gaps** (qa's `tests.md > Edge-case gaps` — reachable inputs the spec left undefined): non-blocking ones need no action here; they stay in `tests.md` and `retro` lifts them into follow-ups. If qa flags one **blocking** (reachable security/data-integrity path), treat it like a blocking finding → `AskUserQuestion`: define the behaviour (→ back to `engineer`/`pm`) or accept the risk (→ carry into `retro.md`).
      - **Coverage floors** (qa's `tests.md > Coverage (diff vs floor)` — unit 80% / integration 70% / e2e 50% of critical journeys, each only where in scope). At/above floor or out of scope → no action. Any **below-floor** level → escalate via `AskUserQuestion`: accept the gap (→ `retro.md` follow-up) or send back to `engineer` for the missing tests (bumps `cycles.test`, same 3-cycle budget). **Advisory, not failing tests** — never sets status `failing` or blocks ship on its own, and never pad coverage with trivial tests.
    - `chore` / `docs` → spawn `qa` with mode = `Skipped`; qa writes a one-line stub in `tests.md` explaining why and returns.
    - `spike` → skip entirely. Engineer's `recommendations.md` is the deliverable.
14. **Docs touch-up.** Spawn `engineer` in docs mode (skipped for `spike`; light for `fix`/`refactor`/`chore` — pass that hint).
15. **Ship.** Spawn `engineer` in ship mode. Pass `open_pr_on_ship` from state. Engineer stages, writes a commit message referencing the run ID + goal, and (if requested) opens a PR. The engineer **returns** the commit hash + PR URL; **you** record them in `state.json` (single-writer discipline — workers never write state) so `retro` can lift them.
    - **Ship check** (skip when `repo_root` is null or the engineer returned "no VCS — ship skipped"). Run `git -C <repo_root> log --oneline -1` and confirm the commit SHA the engineer reported is present. If the log shows no new commit, re-spawn `engineer` in ship mode.
    - **CI check (PR runs only).** If a PR was opened and CI status is reachable from this session, confirm the checks pass before step 16. **Probe in this order — most-available first:** (1) a GitHub/CI MCP tool (remote environments typically have these and no `gh`), (2) a PR-activity subscription if the environment offers one, (3) the `gh` CLI (`gh pr checks`) where it exists. A CI failure routes back to `engineer` with the failing job's log excerpt and bumps `cycles.test` (same budget + escalation as step 13). If none of the three is available or the repo has no CI, write `ci: unchecked` in `state.json > notes` and proceed — never block on infrastructure that isn't there.
    - Skipped for `spike` unless the user explicitly opted to commit at the gate.
16. **Retro.** Spawn `retro`. INDEX status → `done`, set finished date. State: `step=retro, next_step=skill-handoff`. **For a multi-repo run, pass the changed-repo set in the prompt** so `retro` reads each changed repo's diff (`git -C <r> …`), not just `repo_root`'s — its reflection must cover the whole run. Retro is a **single multi-repo-aware pass, not a per-repo fanout** (it synthesises the already-unified `review.md`/`tests.md`/`security.md` per-repo sections and skims each diff; it also holds no `Agent` tool, so there are no helpers to dispatch).
17. **Skill-candidate handoff.** Read `retro.md > Skill candidates`. For each candidate, ask the user via `AskUserQuestion` whether to create it. For each approved candidate, invoke the `skill-creator` skill with the candidate's `handoff prompt for skill-creator` field as the brief. Record outcomes in `retro.md > Skill candidates` (`status: created | skipped | deferred`).
18. **Done.** Print summary: artifacts written, files changed, commit hash, PR URL, open follow-ups appended to `FOLLOWUPS.md`, skills created. State: `phase=done, step=done, done_at=<ISO timestamp>`.

## Fanout dispatch

The `/dev` workflow's main agent and `pm`, `lead`, `qa`, and `engineer` sub-agents can request parallel team-agent fanout for the independent-sub-investigation case (spec research, plan integration points, review, security buckets, test categories, implement phases). The full pattern lives in `.claude/skills/fanout-team-agents/SKILL.md`; this section is the orchestrator's (main agent's) consumer-side contract.

**Direct nesting is the primary path (v2.1.172+).** The splittable agents (`pm`, `lead`, `qa`, `engineer`, and the self-splitting `team-*` workers) now hold `Agent` and **self-dispatch their helpers directly** — each carries a "Recruit help when the work is large" section. So a worker returning to you may already have run its own fanout. The `FANOUT_REQUESTED:` consumer contract below is the **fallback**: it handles the case where a worker prefers you to dispatch, and it remains the path for **background implement-fanout** (where phase-granular `state.json > impl_phases_done` resume is wanted). One exception where you still lead: **plan-prep push (step 8)** is the primary path for plan integration-point mapping — `lead` dedups against it.

### Surface (per-repo) fanout — orchestrator-owned outer loop, no signal

The two fanout axes above split **one repo's** work: the *lens* axis (6 review workers / security buckets) and the *category* axis (test categories) both fan out within a single `repo_root`. A **control-plane run that spans multiple repos** adds a third, orthogonal axis: **surface** — split the three read-and-judge phases **review (step 11), security (step 12), and test (step 13)** **per repo** so N repos are read in parallel instead of one agent crawling them serially (the slow path the user hit). This is **never a `FANOUT_REQUESTED:` signal** — no sub-agent discovers it mid-work; **you (the orchestrator) already know the repo list at dispatch time** from `state.repos`, so you lead it directly, exactly like plan-prep push. (**Retro (step 16)** is the fourth phase that reads across repos, but it is **multi-repo-aware single-pass, not surface-fanned** — it synthesises the already-unified per-repo artifact sections and holds no `Agent`, so there is nothing to parallelise; see step 16.)

The mechanics (full per-step detail in steps 11, 12, and 13; this is the shared contract):

- **When.** The run's changed-repo set (repos in `state.repos`, else `[repo_root]`, that this run actually changed) has size > 1. Size ≤ 1 → the single-repo path, unchanged. (Security additionally narrows to the subset of changed repos that trip sensitive paths — its *security-review set*.)
- **Dispatch.** One `lead` (review or security) / `qa` (test) per changed (or, for security, tripping) repo, **`run_in_background: true`, all in one message**, each scoped to that repo via `repo_root=<r>` and the agent's **Per-repo variant**. Background follows implement-fanout's precedent and is safe regardless: its documented rationale is that a foreground batch of these `pm|lead|engineer|qa|retro` `subagent_type`s self-blocks on the 2nd spawn under `dev-agent-guard.sh` Case 3 (inferred from the implement-fanout note, not separately re-verified). **Cap 6**; group beyond.
- **No naive composition with the lens/category axes.** Per-repo reviewers/testers are **single-pass** by default — do not nest the 6-lens or per-category fanout inside each (that multiplies to 6×N agents). Reserve the inner axis for a single repo whose own diff is genuinely non-trivial, and keep the total within the concurrency cap.
- **Synthesis.** After all return, write `state.json`, then **foreground re-spawn one** `lead`/`qa` in the **Surface-synthesis variant** → it writes the single unified `review.md`/`security.md`/`tests.md` with one `### Repo: <path>` subsection per repo plus the global anti-bias / AC-coverage walk (security aggregates `fix-required` iff any repo has a `high`). **Aggregate verdict/status = pass/passing iff every repo passes.** The cycle counter (`cycles.review` / `cycles.test`; security high-loops bump `cycles.review`) bumps **once per fanout, per run** — never per repo.
- **Non-primary-repo findings dead-end (all three phases).** `engineer` and ship are scoped to the primary `repo_root`, so a blocking review finding, a failing test, or a `high` security finding in a **non-primary** repo has **no auto-fix path** — surface it to the user (`AskUserQuestion`) instead of routing to `engineer`, which would edit the wrong repo. Never downgrade a real `high` to fit the boundary.
- **Resume is fanout-granular, not per-repo.** Review, security, and test write no production code, so a mid-fanout `--resume` simply re-runs the whole per-repo batch. There is deliberately no `review_repos_done`/`security_repos_done`/`test_repos_done` analog to `impl_phases_done` — the per-phase resume machinery is only worth its complexity for implement, which mutates the tree.

Scope boundary (intentional): branch creation, implement, gate, and ship still operate on the single primary `repo_root`. Surface fanout parallelises only the **read-and-judge** phases (review / security / test) plus retro's multi-repo-aware read, which is safe because the diffs across repos already exist by the time those phases run. Full multi-repo targeting is a tracked follow-up (`FOLLOWUPS.md` F0001), not part of this axis.

### Recognising the signal

After every sub-agent return, scan the **first line** of the return: (a) case-insensitive `FANOUT_REQ` prefix → fanout signal (validate below); (b) `BLOCKER:` prefix → blocker (surface to user); (c) `SIZE_UPGRADE:` prefix → size upgrade (handle per `## Size-aware execution`); (d) else → success. Before **advancing to the next step**, run the step's **Return check** if one is defined below. Return checks run **only** on the step's primary worker return (`pm` / `lead` / `engineer` / `qa` / `retro`) — **never** on intermediate `team-*` fanout workers, whose returns are collected for the synthesis re-spawn per `## Fanout dispatch` (the artifact doesn't exist until synthesis runs, so a check there would false-positive). A Return check is a presence/shape **tripwire**, not a quality review (that's the `lead` review and `qa` test gates) — it fires at most **one** corrective re-spawn; if the check still fails after that, escalate to the user via `AskUserQuestion` rather than looping. If a fanout signal is present, validate against the strict allowlist:

```text
^FANOUT_REQUESTED: (review|security:[a-z0-9,\-]+|plan:[a-z0-9,\-]+|test:[a-z0-9,\-]+|implement:[a-z0-9,\-]+|research:[a-z0-9,\-]+)$
```

If the first line matches the case-insensitive `FANOUT_REQ` prefix but does **not** match the strict regex (typos, casing, payload-shape errors), this is a **BLOCKER** — surface to the user via `AskUserQuestion` with the offending line and the 6 valid shapes. Do **not** silently fall through to non-fanout. The typo modes this catches: `FANOUTREQUESTED:` (missing underscore), `Fanout_Requested:` (case-mixed prefix), `FANOUT_REQUESTED:review` (no space after colon), `FANOUT_REQUESTED: REVIEW` (uppercase payload), `FANOUT_REQUESTED: review extra` (trailing junk), `FANOUT_REQUESTED: foo` (unknown payload).

### The 6 documented payload shapes

| Shape | Trigger phase / mode | Dispatch |
|-------|----------------------|----------|
| `FANOUT_REQUESTED: review` | Phase 2 step 11 — `lead` Mode B (**default** for a non-trivial diff: large, cross-module, critical, type/contract/test-sensitive, or uncertain; single-pass only for a small/low-risk diff) | Spawn the 6 review-focused `team-*` workers against the diff |
| `FANOUT_REQUESTED: security:<bucket-list>` | Phase 2 step 12 — `lead` Mode C (**default** when ≥ 2 buckets trip; single-pass for one bucket) | One `team-code-reviewer` per bucket with a focused threat-model prompt scoped to that bucket's paths |
| `FANOUT_REQUESTED: plan:<point-list>` | Phase 1 step 8 — `lead` Mode A (**default** for S/M/L existing-code work with independently-researchable points; single-pass for XS / pure-greenfield / one straightforward change) | For each point: one `team-codebase-explorer` pass for current state + one `team-best-practice-researcher` pass for current best practices — **but skip the `team-codebase-explorer` for any point the push-based plan-prep already mapped; re-dispatch only the residual `team-best-practice-researcher` (see step 8)** |
| `FANOUT_REQUESTED: test:<category-list>` | Phase 2 step 13 — `qa` (**default** when ≥ 2 of {unit, integration, e2e} AND any ≥ 3 tests) | One `team-pr-test-analyzer` per category |
| `FANOUT_REQUESTED: implement:<parallel-phase-list>` | Phase 2 step 10 — `engineer` Mode A (**feat-only**, default when the plan declares ≥ 2 `Parallelizable: yes` phases) | **Gate** on `Type==feat`, then **verify** the named phases' `Files touched (exclusive)` are pairwise-disjoint and every `Depends on` is `none` — refuse + fall back to single-pass engineer otherwise. Dispatch one **write-only** `engineer` (Parallel phase variant) per phase **background, one message** (`run_in_background: true` — `dev-state-mark.sh` skips the marker so no Case-3 self-block; write `state.json` + append `impl_phases_done` as each completion lands). Then foreground-spawn `engineer` in the **Integration variant** to wire shared glue + install deps + run every `verify:` + tick ACs. Resume is **phase-granular** (`impl_phases_done`), not sub-step — a mid-phase interrupt re-runs that phase. |
| `FANOUT_REQUESTED: research:<question-list>` | Phase 1 step 7 — `pm` return-signal, plus step 6 spec-prep fanout from the main agent | One `team-codebase-explorer` per `codebase-*` question and one `team-best-practice-researcher` per `best-practice-*` question. pm cannot dispatch directly — pm returns `FANOUT_REQUESTED: research:<…>` **after writing a draft `spec.md`** (draft-first); orchestrator dispatches, then re-spawns pm to **read its own draft `spec.md`** (digest/Q&A already folded in) plus the findings and refine in place — see step 7. |

### The dispatch pattern (parallelism)

Once the signal validates, dispatch **all workers in the same orchestrator message** — Claude Code's `Agent` tool runs them concurrently when multiple invocations appear in one assistant turn. Sequential `Agent` calls across multiple turns are **not** parallel.

```
# In one orchestrator message — example: the review fanout's 6 workers:
Agent(subagent_type="team-code-reviewer",            description="...", prompt=<focused-prompt-1>)
Agent(subagent_type="team-code-simplifier",          description="...", prompt=<focused-prompt-2>)
Agent(subagent_type="team-comment-analyzer",         description="...", prompt=<focused-prompt-3>)
Agent(subagent_type="team-pr-test-analyzer",         description="...", prompt=<focused-prompt-4>)
Agent(subagent_type="team-silent-failure-hunter",    description="...", prompt=<focused-prompt-5>)
Agent(subagent_type="team-type-design-analyzer",     description="...", prompt=<focused-prompt-6>)
```

Each shape dispatches **its own worker set** (the table above is authoritative) — e.g. `plan:<point-list>` sends one `team-codebase-explorer` + one `team-best-practice-researcher` per point, never the review six. The one-message rule applies to every shape.

Each prompt is **self-contained** (the workers inherit none of the calling sub-agent's context). Include scope (paths / diff slice), goal (one sentence), constraints (what NOT to do), and output shape (the worker's documented section format from `.claude/agents/team-<role>.md`).

### Registry-not-refreshed fallback

If any `team-<role>` spawn fails with `Agent type 'team-<role>' not found`, the registry is session-scoped and the freshly-created `team-*.md` files are not yet discoverable. Two correct responses:

1. **Session restart** — close and re-open the Claude Code session so the registry picks up the new files; then retry `subagent_type="team-<role>"`.
2. **Inline fallback** — re-issue every worker spawn with `subagent_type="general-purpose"` and the worker's role contract read inline into the prompt: read `.claude/agents/team-<role>.md` end-to-end and prepend the body to the focused prompt. Parallelism is preserved (still one message, six `Agent(...)` calls). Record the actual `subagent_type` you used for each spawn — you'll need it for the synthesis step below. Full caveat in `.claude/skills/fanout-team-agents/SKILL.md > Operational caveats > Agent registry is session-scoped`.

### Re-spawn for synthesis

When every worker returns, re-spawn the calling sub-agent (`pm` / `lead` / `qa` / `engineer`) with:

- The workers' outputs concatenated into the prompt (one labelled block per worker).
- A `Dispatched-as:` map: one line per worker, `team-<role> → <actual subagent_type that ran>` (so the calling sub-agent can fill the mandatory `**Dispatched-as**:` provenance line on each `### team-<role>` subsection of the artifact — see `.workflow/_templates/review.md > Per-agent findings`).
- **Re-include any prompt-only context the first spawn carried**, because the re-spawned sub-agent inherits none of it — but prefer durable artifacts over prompt re-passing. For `pm` nothing requirement-bearing is re-passed: pm wrote a draft `spec.md` first (draft-first) and re-reads it (digest/Q&A folded in), so the re-spawn only carries the worker findings. For `lead` / `qa` / `engineer` the inputs they read from disk (`spec.md` / `plan.md` / diff) already carry the requirements, so only re-pass genuinely prompt-only context (e.g. review findings being addressed).

The re-spawned sub-agent does the synthesis (spec discovery notes; plan current-state / research notes; per-agent sections + its own plan-adherence / AC / coverage / integration pass).

### Where fanout fires

The steps that can fire a fanout (signal originated by the main agent or spawned sub-agent, dispatched here):

- **Step 6 — Spec prep** — **default** (per `## Delegation-first`): main agent dispatches `team-codebase-explorer` / `team-best-practice-researcher` before the interview whenever the intent names existing code, integration points, APIs, security-sensitive paths, unfamiliar domain terms, or 2+ independent research questions. Single-pass only for XS pure-greenfield work with no unfamiliar domain/API choices.
- **Step 7 — Spec** — `pm` may return `FANOUT_REQUESTED: research:<question-list>` if it needs codebase or best-practice probes before writing `spec.md`.
- **Step 8 — Plan** — two paths. **(a) Push-based plan-prep (preferred for speed):** before the `lead` spawn, the orchestrator dispatches one `team-codebase-explorer` (haiku) per integration point in parallel for M/L existing-code work with ≥ 2 integration points, then spawns `lead` once with the findings — this keeps the slow LSP-walk off `lead`'s critical path. **(b) Pull-based fallback:** `lead` Mode A may still return `FANOUT_REQUESTED: plan:<point-list>` for anything prep did not cover (typically best-practice research); the orchestrator dispatches the residual workers and re-spawns `lead`.
- **Step 10 — Implement** — `engineer` returns `FANOUT_REQUESTED: implement:<parallel-phase-list>` by default when the plan declares ≥ 2 `Parallelizable: yes` phases (**feat-only**). Orchestrator gates on `feat`, verifies the exclusive Files-touched are pairwise-disjoint, dispatches write-only phase-engineers in the background, then a foreground integration engineer; see the table row + step 10 contract above.
- **Step 11 — Review** — `lead` Mode B returns `FANOUT_REQUESTED: review` by default for a non-trivial diff (deserves independent specialist passes); it writes `review.md` directly only for a small/low-risk diff.
- **Step 12 — Security review** — `lead` Mode C returns `FANOUT_REQUESTED: security:<bucket-list>` by default when ≥ 2 buckets trip (single-pass for one bucket).
- **Step 13 — Test** — `qa` returns `FANOUT_REQUESTED: test:<category-list>` by default when the suite splits (≥ 2 categories AND any ≥ 3 tests).

## Cycle escalation

- Review cycles: max 2. Escalate clearly via `AskUserQuestion`: "Review still has blocking findings after cycle 2. Continue / hand off to me / abort?"
- Test cycles: max 3. Same pattern.
- Don't silently iterate beyond limits. Don't downgrade severity to fit.

## Rules

- Never invent requirements. Ambiguity → `AskUserQuestion` (≤4 questions per batch; one batch by default, a bounded dig loop of at most 3 narrowing batches when ambiguity is genuinely high — see step 6).
- **Never skip the interview.** A spec built from a one-line intent alone is a broken run. Step 6 is mandatory for every fresh run, even short intents.
- Never skip phases that the type matrix says should run. Skipping that's allowed by the matrix is recorded in `state.json > skipped_steps`.
- The gate is non-negotiable.
- **Never spawn an `orchestrator` sub-agent.** That sub-agent does not exist (and could not work — a sub-agent can't call `AskUserQuestion`, so it can't run the interview the orchestrator owns). File-writing workflow `Agent` calls go to `pm`, `lead`, `engineer`, `qa`, or `retro`; fanout-only read/research calls may go to `team-*` workers.
- **Never fall back to `subagent_type: "general-purpose"` for /dev work.** Every file-writing step goes to one of the five named workers. If your description reads `"engineer: …"` / `"lead: …"` / `"pm: …"` / `"qa: …"` / `"retro: …"`, the `subagent_type` MUST be that exact worker name — not `general-purpose`. The `PreToolUse` hook at `.claude/hooks/dev-agent-guard.sh` enforces this and will block the call with a retry message. Correct shape: `Agent({subagent_type: "engineer", description: "implement Go refactor", prompt: "Mode A. Type=refactor. …"})`. The mode hint (`plan`/`review`/`security`, `implement`/`docs`/`ship`, etc.) goes in the *prompt*, not in the description.
- Keep your user-facing text to status updates: which phase, which agent, what's next. One sentence each. The exception is the gate summary, the interview batch, and the final summary, which are spec-shaped.
- End-of-turn: artifacts written + files changed + commit/PR + open follow-ups from `retro.md` + skills created. Nothing else.
