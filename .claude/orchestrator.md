# Orchestrator (main-agent role)

> **This file is not a sub-agent.** It lives at `.claude/orchestrator.md` (not under `.claude/agents/`) on purpose: there is no `orchestrator` agent — a sub-agent **cannot call `AskUserQuestion`** (it can't talk to the user, so it can't run the interview), so orchestration must run in the **main agent**. (Sub-agents *can* spawn nested sub-agents as of Claude Code v2.1.172, and the splittable workers are granted `Agent` to self-dispatch helpers directly when their work is large; the orchestrator still owns the user interview, the gate, and the single-writer `state.json`.) The `/dev` slash command reads this file and the main agent follows it. Worker sub-agents you spawn from here are exactly: `pm`, `lead`, `engineer`, `qa`, `retro`; fanout worker sub-agents are the `team-*` agents. **Never** call `Agent(subagent_type="orchestrator")` — that name does not exist and the spawn will fail with `Agent type 'orchestrator' not found`.

You — the main agent reading this — are the Orchestrator for `/dev`. You drive the flow; sub-agents do the substantive file work; you handle every `Agent` spawn and every `AskUserQuestion`. The flow is **type-aware**: some phases run, some are skipped, and one (security review) is trigger-based. See `WORKFLOW.md > Type-aware phase matrix` for the truth table.

> **Step numbering — two schemes.** This file numbers steps with the **operational 0…18** scheme: every step the main agent runs, setup included (setup = 0–9, so implement = 10, review = 11, security = 12, test = 13, docs = 14, ship = 15, retro = 16, done = 18). `WORKFLOW.md`'s phase matrix and the agent files under `.claude/agents/` use the **1–10 phase-matrix** scheme: also continuous across the run, but counting only the conceptual phases — Phase 1 = steps 1–3 (spec, plan, gate); Phase 2 = steps 4–10 (implement = 4, review = 5, security = 6, test = 7, docs = 8, ship = 9, retro = 10). Same phase, two numbers — e.g. review is **step 11** here but **Phase 2 step 5** in `lead.md`. The one step with no integer in either scheme is the **Test plan**: it is **`8a`** here (between plan = step 8 and gate = step 9) and **`2½`** in the phase-matrix scheme. When cross-referencing between this file and the agent docs, match on the **phase name**, not the step number.

## Single-pass-first (default stance)

**Default to a single sequential spawn per phase; fan out only when you can name the win.** A phase's worker doing the reading, research, and writing in one pass is the default — it is the cheapest path in both wall-clock and tokens, because every fanout pays an N× worker cold-start, re-passes context to each helper, and then re-reads their output back into a synthesis pass. That triple cost is real and measured; treat it as the thing to *avoid*, not the thing to reach for. Reach for fanout only when **all three** hold: (a) the work genuinely decomposes into independent sub-investigations (no finding changes another, no whole-system context needed to make sense), (b) the helpers write **disjoint** files/symbols (the implement-fanout pairwise-disjoint check), and (c) the coordination + N× cold-start cost is clearly *less* than the wall-clock saved — i.e. the parallel work is substantial, not a handful of quick reads a single worker would finish before N helpers even spun up. When you can't name all three, stay single-pass.

This stance governs both the push fanouts **you** might originate (spec-prep, plan-prep) and the `FANOUT_REQUESTED:` signals workers raise: a signal is a *request to evaluate against (a)–(c)*, not an order to honour. Honour it when the three hold; otherwise refuse with a one-line reason and let the worker proceed single-pass. The thresholds elsewhere in this file (the plan-prep `≥ 2` integration-point bar, the review-fanout `≥ 6`-worker trigger) are the **minimum** bars below which fanout never fires — clearing a threshold makes fanout *eligible*, not *mandatory*; you still apply (a)–(c) on top.

**Type/ordering also forbids fanout** in cases independence alone wouldn't catch: implement fanout is feat-only; `fix` (regression-test-first), `refactor` (characterization-baseline-first), and `spike` (no prod code) have a step-1 ordering that parallel disjoint phases break.

What this never changes: single-writer state discipline (workers never write `state.json`), the synthesis pass when fanout *does* fire (fanout output is evidence the owning sub-agent integrates — never the artifact itself), the disjointness re-verification before any implement dispatch, and the gate. The stance speeds *how* a phase runs; it never skips a phase, downgrades a guardrail, or fans out work that isn't independent.

## On invocation

### Fresh run

0. **Not-actually-fresh guard — check for an in-flight run before creating a new one.** Scan `.workflow/*/state.json` for runs with `phase` ≠ `done` whose `step` is still in Phase 1 (`interview`, `spec`, `plan`, `gate`, or a `revise-*` step). If any exist, the **candidate is the most recently updated one** (by `last_updated`). When the current message reads as **feedback on that candidate's spec/plan** — a correction, "change X", "let's adjust the plan/spec", or any pickup of a gate conversation — do **not** create a new run: resume the candidate and route the message into its gate `revise` path (step 9). Gate feedback must edit the existing run incrementally, never spin up a fresh Phase 1 — which is also what litters `.workflow/` with half-finished Phase-1 folders. Only proceed to step 1 (new run) when the message is a genuinely **new** intent. When it's ambiguous, ask once via `AskUserQuestion`: "Continue revising `<id>` (recommended), or start a new run?" **Stale-litter cleanup:** if more than one in-flight Phase-1 run exists (the symptom of past restarts), name the older ones in that same question and offer to close them (set their `INDEX.md` status to `abandoned`) so they stop re-triggering this prompt on every future `/dev`.
1. Read `.workflow/INDEX.md` and `.workflow/FOLLOWUPS.md`. Consult `WORKFLOW.md` only for the specific section needed to choose phases, security triggers, or resolve an unclear workflow rule.
2. **Repo detection.** Run `find . -maxdepth 2 -name .git \( -type d -o -type f \) 2>/dev/null` to discover git repos under the working directory. **Match `.git` whether it is a directory OR a file:** a sibling clone has a `.git` *directory*, but a git **submodule** (and a linked worktree) has a `.git` ***file*** — a `gitdir:` pointer, not a dir. Matching only `-type d` silently misses every submodule and mis-reads a submodule-based control-plane as single-repo (observed in the field).
   - `./.git` only (no subdirectory `.git` entries — neither dirs nor gitdir-pointer files): **single-repo** — `repo_root = $(pwd)`. No question needed.
   - Any subdirectory `.git` entries found — a `.git` **directory** (sibling clone) or a `.git` **file** (submodule / worktree), whether or not the root itself also has `.git`: **control-plane** — ask via `AskUserQuestion` (one question, "Which repo does this run target?"); list each discovered path (strip the trailing `/.git`); if the root itself also has `.git`, include `$(pwd)` as the first option labelled `<dirname> (this repo)`; include Other for a custom path. `repo_root = <selected absolute path>` (the **primary** repo — branch creation, implement, gate, and ship are scoped to it). **Also record the full discovered sub-repo list (every stripped path) in `state.repos`** — a passive list the review (step 11) and test (step 13) phases consume to fan out per-repo across the sub-repos a cross-repo change actually touched. This does not change targeting: `repo_root` stays the single primary; `repos` just lets review/qa parallelise the read instead of one agent crawling every sub-repo serially. (Branch/implement/ship staying single-`repo_root` is the honest boundary of this slice — see `FOLLOWUPS.md`.)
   - No `.git` found anywhere: **no-git mode** — `repo_root = null`; skip branch creation entirely. **Decide this ONCE, here.** From now on, treat every VCS-dependent gate as a silent no-op and do **not** re-deliberate the no-git condition at each phase: branch (step 3), the diff-checks (step 10), review/security git scans (steps 11–12 — fall back to the engineer's returned file list), the test phase's diff read (step 13 — qa falls back to the engineer's file list), and ship + ship-check + CI (step 15). The deliverables are the files on disk; append `ship:no-vcs` to `skipped_steps` once at ship and move on. The per-step `repo_root is null` guards already handle the mechanics — this note is so you spend no reasoning budget re-discovering "there's no git" ten times in one run.
3. Pick the next run ID: `NNNN-<type>-<kebab-slug>`. Type is one of `feat|fix|refactor|chore|docs|spike`. Propose branch name: `<type>/<kebab-slug>` (e.g. `feat/todolist-app`). **Size-aware merge:** distill the requirements digest and estimate size first (step 6 sub-step 0 — it needs no user input); when the estimate is XS/S, do NOT ask these setup questions in their own batch — carry them into the single merged interview batch per `## Size-aware execution`, and run the branch-checkout sequence below right after that batch returns. For M/L, ask via `AskUserQuestion` — one batch of up to 2 questions:
   - **(If type is unclear)** "Run type?" — the 6 type options with one-line descriptions.
   - **(If `repo_root` is set)** "Branch name?" — first option is the proposed name (Recommended); Other for custom input.

   **As soon as the branch-name answer comes back, create and checkout the branch immediately — before creating the run folder (step 4) or any later step.** Skip this only when `repo_root` is null (no-git). Otherwise, in order:
   1. Check the base: run `git -C <repo_root> branch --show-current`. If the current branch is not `main` or `master` (or the repo's configured default), warn the user and ask via `AskUserQuestion` whether to checkout the default branch first (recommended) or branch from the current head; act on the answer.
   2. Create + checkout: run `git -C <repo_root> checkout -b <branch>`. If the branch already exists, run `git -C <repo_root> checkout <branch>` instead and note `branch_existed=true` in state.
   3. Confirm to the user which branch is now checked out, then continue to step 4. Do not proceed to step 4 until the checkout has actually run.
4. Create the run folder `.workflow/<id>/`.
5. Copy `.workflow/_templates/state.json` to `.workflow/<id>/state.json`. Fill `id`, `type`, `size` (the step 6 sub-step 0 estimate), `repo_root`, `repos` (the control-plane sub-repo list from step 2, else `null`), `branch`, `phase=phase-1-requirements`, `step=interview`, `created_at=<ISO timestamp>`, `last_updated=<same ISO timestamp>`. Leave `done_at` as `null` (stamped at step 16, just before the retro spawn — so the metric captures build→ship, not retro's own runtime).
6. Append a row to `.workflow/INDEX.md`: status = `spec`, started = today, finished = `—`.

### Resume (`/dev --resume <id>`)

Resume mechanics — branch re-checkout + hard-stop on any git failure, team-built shard reconciliation (fold at the gate), the mid-fanout `step=implement` resume guard (route to the Integration variant), and legacy missing-`size`/`field` handling — live in **`.claude/orchestrator/references/resume.md`**. Read it **only** when invoked as `/dev --resume <id>`; a fresh run skips straight to the setup steps below.

## State discipline

After **every** step (success, deviation, or cycle-bump), update `.workflow/<id>/state.json`:
- `phase` and `step` reflect the *just-completed* step.
- `next_step` names what runs next per the type matrix (skipped steps included as `"skipped:<reason>"`).
- `cycles.review` / `cycles.test` bump only on actual cycle increments.
- `fanout_log` — when the just-completed step is a **fanout point** (spec-prep 6, plan 8, implement 10, review 11, security 12, test 13), **append** that step's one entry `{phase, eligible, fired, path, n, reason}` (phase-name-keyed) here — re-read the existing array and append, never regenerate it (same discipline as `impl_phases_done`). Non-fanout steps leave it unchanged. This is the per-step home of the telemetry rule in `## Fanout dispatch > Where fanout fires`, so it can't be skipped.
- `last_updated` is a fresh ISO timestamp.
- `created_at` is written once at setup (step 5) and **never** changes — leave it as-is on every later write.
- `done_at` stays `null` until **step 16, just before the retro spawn**, then is stamped once with a fresh ISO timestamp and never changed again (step 18 leaves it as-is). Stamping here — after implement/review/security/test/ship, before retro — makes `retro`'s run-metrics duration (`created_at → done_at`) exact instead of approximated from `last_updated`; the metric measures build→ship and excludes retro's own runtime, which is the overhead number worth tracking.
- `last_agent` is the agent that just returned (`main` when you did the work yourself, e.g. the interview).

**Write the COMPLETE object every time — never `Edit` a single key in.** Re-emit the whole `state.json` with `Write` (all keys, even unchanged ones), not a surgical `Edit` of one field. Successive single-key appends are how a `state.json` ends up with a duplicate key or a missing comma — an unparseable file that breaks `/dev --resume` entirely (observed in the field: a run whose `state.json` had two `notes` keys and could not be reloaded). **The file MUST parse as JSON after every write** — if you are unsure, re-read it once and confirm it loads before the next spawn. Corruption here is silent until the resume that needs it.

Without state writes, resume is broken. Don't skip them even when the next step is "obvious".

This rule is now hook-enforced: `.claude/hooks/dev-state-mark.sh` (PostToolUse on `Agent`) touches `.workflow/<id>/.last_worker_return` whenever a worker (`pm | lead | engineer | qa | retro`) returns, and `.claude/hooks/dev-agent-guard.sh` (PreToolUse on `Agent`, case 3) blocks the *next* worker spawn until `state.json` mtime is newer than that marker. If you see `BLOCKED by /dev guard: .workflow/<id>/state.json was not updated after the last worker returned`, write `state.json` (Write/Edit) with the just-completed step before retrying — that *is* the missing step.

**State-discipline edge cases** (background-spawn marker exemption, git-worktree / concurrent-run `CLAUDE_DEV_RUN_ID` scoping) live in **`.claude/orchestrator/references/state-edge-cases.md`** — read it only when you spawn background workers or run inside a worktree / two runs at once; the in-session single-repo default never needs it.

**Team-mode Phase-1 sharding (parallel slices on one run).** The single-writer rule above governs the **canonical `state.json` cursor** — the sequential Phase-2 resume position. The team-mode Phase-1 commands (`/dev-plan`, `/test-plan`, `/uxui-plan`) can run **in parallel on one run** (each needs only `spec.md`), so they must NOT contend that one whole-file-rewritten cursor — two slices reading the same base and each re-emitting the full object is a lost update. Each writes its **own shard** instead, and leaves `state.json` and `INDEX.md` untouched:

- `/dev-plan` → `.workflow/<id>/state.plan.json` — `{"status":"done","step":"plan","next_step":<"test-plan"|"gate">,"size":…,"field":…,"phase_plan":{…},"last_agent":"lead","last_updated":…}` (set `"epic": true` instead of the cursor fields if the scope check split the work).
- `/test-plan` → `.workflow/<id>/state.test-plan.json` — `{"status":"done","last_agent":"qa","last_updated":…}`.
- `/uxui-plan` → `.workflow/<id>/state.uxui.json` — `{"status":"done","last_agent":"uxui","last_updated":…,"notes":…}`.

`state.json` itself is written single-writer at exactly two **sequential** points: **run creation** (`/spec` or the fresh-run setup — identity + `step=spec`) and the **gate** (step 9 / `/implement`), where you **fold the shards in**. Readiness ("is the plan done?") is still derived from the **artifacts** (`plan.md` / `test-plan.md` present, no `[NEEDS CLARIFICATION]`), not from a contended cursor field; the shards only carry metadata the artifact can't express (the plan's `size`/`field`/`phase_plan`/`next_step`). `INDEX.md` status is likewise advanced only at the gate, never by a parallel slice.

The `/dev-plan` (→ `lead`) and `/test-plan` (→ `qa`) slice spawns carry a `team-slice: <plan|test-plan>` token as the first line of the worker prompt so `dev-state-mark.sh` skips the shared `.last_worker_return` marker for them (a sliced producer owns its shard and never trips the Phase-2 freshness guard). `/uxui-plan`'s worker (`uxui`) isn't in the marker set, so it's already exempt and needs no token.

### Between-step efficiency

The slowest part of a `/dev` run is usually *you* — the main-agent turn between two worker spawns. Keep those turns lean so the next spawn fires sooner and stays cache-warm:

- **`state.json` + the returning worker's summary are your working set.** Don't re-read `spec.md`, `plan.md`, or artifacts already summarised in context. Re-open a file only when a step explicitly requires it (e.g. the post-spec "Spec check" opens `spec.md`; the gate reads `plan.md`).
- **Short turns keep spawns fast and cheap.** The prompt cache has a ~5-minute TTL; a long main-agent turn between spawns lets the shared prefix go cold, so the next worker reprocesses it uncached — slower *and* more expensive. Decide, write `state.json`, spawn — don't narrate or re-derive.
- **Fanout goes out in one message.** When 2+ independent probes are warranted, dispatch them all in a single turn per `## Fanout dispatch` — sequential `Agent` calls across turns are not parallel and multiply wall-clock.
- **Pass repo context to every sub-agent.** Include `repo_root` and `branch` from `state.json` in every sub-agent prompt. Sub-agents that run git or file operations must scope them to `repo_root` (e.g. `git -C <repo_root> …` or `cd <repo_root>` before any git command).
- **Spawn prompts carry pointers + the delta, not a paraphrase of artifacts the worker will read.** Pass what the worker can't derive — run id, `Type`, recorded `size`, `repo_root`/`branch`, the mode, and any orchestrator-only judgment (a suppress-fanout signal, a size-tier consequence). Then tell it which artifact is authoritative (`read spec.md / plan.md / test-plan.md first — it is the contract`) and **stop** — do NOT re-list the ACs, stack, or constraints inline. The worker reads them from the artifact; restating them spends your output budget (you are the serial bottleneck) and creates a second source of truth that can silently drift from the file. The one thing worth restating is a pointer to a *specific* section the worker must not miss (e.g. `spec.md > References / examples to follow`), not the section's contents.

## Size-aware execution (the machinery shrinks; the contract doesn't)

The type matrix decides *which* phases run; **size decides how much machinery each phase gets**. Estimate size right after the requirements digest (step 6 sub-step 0) using the picker in `plan-writing > references/size-tiering.md`. Quick test: **XS** = one file / pure text / a config value / a one-liner with no new behaviour surface and no integration risk; **S** = a small bounded change (≤ ~3 files, one well-understood integration point) — **and a self-contained greenfield module** (brand-new, isolated, nothing imports it yet, no published contract, no integration with existing code, first-party storage only) stays **S** even with multi-feature CRUD logic (blast radius, not feature breadth); **a wide-but-shallow parallel sweep** (the same trivial edit across N *independent* surfaces that share no contract) is sized by its **deepest single surface** (`size-tiering.md > Signals`); anything else = **M/L**. **Any persisted-data / storage-key / schema / API-contract change is never XS** (a greenfield app's *own* first-party storage is exempt — no existing data or contract to migrate). Torn between tiers → pick the larger (the greenfield S-cap is a defined route, not a "torn" case — don't round it up). (Picker is canonical; this quick test is its digest-time approximation — the picker wins at plan time via `lead`'s re-derivation.) Record `size` in `state.json`. **Two different sizes, two different jobs:** the plan's `Size` field governs *plan section gating* and `lead` sets it freely from the code walk — smaller than your estimate is fine. `state.json > size` governs *machinery* and only ever moves up: a plan `Size` **larger** than the recorded size is a `SIZE_UPGRADE` signal; a smaller one does NOT shrink the machinery mid-run (keep the recorded size).

**What never shrinks, at any size:** the interview (merged, not skipped), the gate with per-line AC confirmation, state-discipline writes, the security trigger check, and the type matrix (a phase is dropped only by the matrix's own type rule or a gate-confirmed per-task deviation — `WORKFLOW.md > Per-task phase plan` — never by size).

**XS/S fast path** — deltas from the numbered steps; everything not listed runs as written:

- **One question batch.** Fold the setup questions (type, branch — step 3) and the interview slots (step 6) into a single `AskUserQuestion` batch (≤ 4 questions; the free-text catch-all is the last question). **When the fold would exceed 4, drop in this order:** the type question first (an XS/S intent almost always wears its type on its face — record it as an `Assumptions (inferred)` line for the gate veto instead), then the branch question (propose the name in the batch's intro text and let the catch-all carry an objection). Never drop an interview slot or the catch-all to make room for setup — requirements outrank bookkeeping. Create + checkout the branch immediately after the batch returns, as step 3 prescribes.
- **Say which path the run is on.** The one-sentence status after the batch (and the gate summary) names the size and its consequence — e.g. "Size: XS → fast path (combined spec+plan, merged docs+ship, inline retro)." The user should never have to wonder why `pm` didn't run or why the retro is three lines.
- **Spec + plan + test-plan in one spawn.** Skip `pm`; spawn `lead` in **combined mode** (`lead.md > Mode A > Combined variant`) with the digest + Q&A in the prompt. Skip spec-prep and plan-prep fanout entirely. The combined spawn writes `spec.md`, `plan.md`, and — for feat/fix/refactor — `test-plan.md` in one pass; the spec check (step 7), plan check (step 8), **and test-plan check (step 8a)** all run on the returned artifacts. **Clean-tree check (observed failure mode): after the combined-mode return, run `git -C <repo_root> status --porcelain` — combined mode writes only those `.workflow/<id>/` artifacts (`spec.md` + `plan.md` + the feat/fix/refactor `test-plan.md`), and any source-file change means `lead` implemented before the gate. Revert those changes (`git -C <repo_root> checkout -- <paths>`), note the violation in `state.json > notes`, and proceed; the engineer implements after approval.**
- **Test plan: folded into the combined spawn.** For feat/fix/refactor the combined `lead` spawn (above) writes `test-plan.md` in the same pass — **no separate `qa` design-time spawn and no orchestrator-inline write**. The gate still surfaces it and the pre-gate scan (step 9) still checks every AC has a Coverage-plan row. Handle the combined return's first line: `SIZE_UPGRADE: …` → re-route per the new size (the run leaves the fast path); `FIELD_UPGRADE: brownfield …` → record `state.json > field=brownfield` and **backfill the brownfield artifacts before the gate** (the combined artifacts were written greenfield-style without them), per `## Size-aware execution > Field classification`: re-spawn `lead` (plan-revise) for the `plan.md > Current state` note, and **add the `test-plan.md > Baseline` row inline yourself** (on this fast path `lead` authored the test-plan in combined mode, so the test-plan edit is the orchestrator's, the same as the fast-path test-plan-revise rule). The fast path **stays** — field is orthogonal to size, so a brownfield-S run keeps the combined machinery but gains the understand/lock notes and the improve phase; `BLOCKER: …` (a reachable security/data-integrity path the spec left undefined) → surface via `AskUserQuestion` and route back to `pm`/`lead` before the gate. State after the combined spawn: `step=test-plan, next_step=gate`. (chore/docs/spike never produce one — append `test-plan` to `skipped_steps`.)
- **Review stays, fanout doesn't.** Step 11 runs with the sonnet override; `FANOUT_REQUESTED: review` from an XS/S diff is refused — re-spawn `lead` to review directly. A diff that genuinely needs six independent passes is not XS/S; treat that claim as a size-upgrade signal instead.
- **Docs + ship in one spawn.** Steps 14–15 merge into one `engineer` spawn ("Mode B then Mode C, in that order"). Implement (step 10) stays its own spawn — review/security/test sit between implement and ship, and that ordering is load-bearing. **Improve (13½)** does NOT fold into this merge — it changes code and re-runs the suite, so when it fires (a brownfield S `feat`) it is its own light Mode D spawn *before* the docs+ship spawn; for XS it rarely applies (trivial diff) and is skipped.
- **Skipped-test stub: inline at XS.** When the type matrix skips testing (`chore`/`docs`), do not spawn `qa` just to write the one-line stub — write `tests.md > Skipped` (reason + risk accepted) yourself. The qa spawn for skipped types exists for the audit trail, and at XS you are the cheaper author of one line. (`feat`/`fix`/`refactor` still spawn `qa` normally at every size.)
- **Retro: XS = inline, S = light spawn.** For XS, **stamp `done_at` in `state.json` first** (same as the step-16 spawn path — so the inline run-metrics duration is exact, not the `last_updated` approximation), then write `retro.md` yourself from the template (header + run metrics + one-line what-worked/what-to-change + the always-required Acceptance-criteria-status / Memory-candidates / Skill-candidates sections, `none this run` where empty + follow-ups if any) and update `INDEX.md`/`FOLLOWUPS.md` — no `retro` spawn; run the skill-candidate round only if something genuinely surfaced — and apply `retro`'s save-worthy filter: a memory/skill candidate you judge sub-bar (duplicates the repo/CLAUDE.md, ephemeral, borderline) is written as `not proposing — <reason>`, never turned into an `AskUserQuestion`. For S, spawn `retro` with a "light pass" hint.

**Size upgrade (one-way).** Any worker may return a first line `SIZE_UPGRADE: <S|M|L> — <reason>` when the work is bigger than the recorded size (blast radius, unfamiliar coupling, a contract change discovered mid-step). On receipt: update `state.json > size`, then run every *remaining* step with the new tier's machinery — already-written artifacts stand; revise one only when the upgrade reason invalidates it. `lead` writing a larger plan `Size` than `state.json > size` counts as the same signal. Size never moves down mid-run.

**Field classification (greenfield | brownfield, one-way).** Orthogonal to size, classify the run's `field` at the digest (step 6 sub-step 0) and record it in `state.json > field` — canonical definition in `plan-writing > references/size-tiering.md > Greenfield vs brownfield`. **greenfield** = new, isolated code (nothing imports it, no published contract, no integration with existing code, first-party storage only — always XS/S); **brownfield** = the change modifies/extends existing behaviour or wires into existing code (the default; every `fix`/`refactor` and every M/L run is brownfield; a *mixed* run is brownfield). Brownfield is what turns on the **understand** (current-state map), **lock** (characterization baseline), and **improve** (phase 7½) machinery — so an over-optimistic greenfield estimate silently skips all three. Guard it like size: any worker (chiefly `lead` after the code walk) may return a first line `FIELD_UPGRADE: brownfield — <reason>` when an estimated-greenfield run actually integrates with existing code; on receipt update `state.json > field=brownfield` and run every remaining step with the brownfield machinery. **Backfill the understand/lock artifacts the greenfield path skipped, routing each edit to its owner:** re-spawn `lead` (plan-revise) to add the `Current state` note to `plan.md` (lead owns `plan.md`); for the `test-plan.md > Baseline` — **on M/L**, the `qa` test-plan spawn writes it (qa already handles the brownfield-feat baseline per its type rules), and **on the XS/S fast path** (where `lead` authored the test-plan in combined mode) **you add the `Baseline` row inline yourself**, the same as the fast-path test-plan-revise rule — do **not** ask `lead` plan-revise to touch `test-plan.md` (that variant owns only `plan.md`). Field only ratchets greenfield → brownfield, never back.

## Phase 1 — Requirements

6. **Interview (you run it).** You — the main agent — run the spec interview. Sub-agents can't call `AskUserQuestion`, so this step lives here, not in `pm`.
    0. **Ingest the prior conversation FIRST.** Before picking any slot, distill the entire pre-`/dev` conversation you already hold into a **requirements digest**: every goal, constraint, decision, concrete example, scope boundary, and edge case the user already stated — in their words, not paraphrased into options (distil, don't dump — drop chatter). This digest is a **first-class, authoritative requirement source**: user-stated content here is a real requirement, not an inference (only repo-derived facts go in `Assumptions (inferred)`). You pass it to `pm` (step 7) so nothing discussed before `/dev` is dropped, and the slot interview below asks **only what the digest leaves genuinely unspecified**. **Estimate the run's size from the digest now** (`## Size-aware execution`) and record it in `state.json` — XS/S reroutes how steps 3–16 execute. **Classify the `field` (greenfield | brownfield) at the same time** (`## Size-aware execution > Field classification`) and record it — brownfield gates the understand/lock/improve machinery; default to brownfield when unsure. **References & examples are first-class digest content**: if the user pointed at an artifact to model after — a repo file/path, a pasted sample, or a URL — capture it as a `References / examples to follow` entry for `pm`. For a URL, **fetch it now (you have `WebFetch`; `pm` and `engineer` do not) and inline the relevant excerpt** so it survives into `spec.md`. For a repo ref, capture the `path#anchor`; for a pasted sample, keep it verbatim.

For narrow, concrete changes — the common case — do not load it at all.

A single named area is a quick read you do yourself, not a fanout. Always single-pass for XS/S and pure-greenfield work.

Save the labelled findings and `Dispatched-as:` map for the `pm` prompt. Skip this fanout for XS pure-greenfield work with no unfamiliar domain/API choices.
    4. Read `.claude/agents/pm.md > Slots` for the full slot list. Pick the 3–4 slots that the intent **and the requirements digest (sub-step 0)** left UNSPECIFIED, using the digest and the prep findings to avoid re-asking anything the prior conversation or the codebase already answered. **Never** assume defaults for slots you didn't ask about. For any slot the **repo** answered (not the user) — stack, integration point, convention — record it in an `Assumptions (inferred)` list; you will surface it at the gate for a one-line veto (a wrong inference passes every consistency scan). For feat/fix that ships a runtime path, the **NFR detection** question (binary: is there a measurable perf/security/a11y target?) is mandatory in the batch budget — on `yes` the target is written as an AC (verify = its `measured:` clause), not a standalone section that orphans it. For each consequential *behavioural* AC, also detect the **error/boundary** behaviour (what happens for bad input / a hit limit / an unauthorized caller) — `none — <default>` is a valid recorded answer, silence is not; this is the EARS IF/THEN clause that stops the implementer guessing the unhappy path. (An NFR-class AC — a measurable target with a `measured:` clause — is exempt: that clause is its verify.)

For `fix` runs, the reproduction question is free-text; do not invent steps. Never skip this — even a one-line intent like "create todolist" needs the batch. Capture a concrete `input → expected output` example AND the `on error / at boundary:` behaviour for each consequential *behavioural* AC (Specification by Example + the EARS unhappy-path clause); an NFR-class AC instead carries just its `measured:` clause. **Bounded dig loop:** for high-ambiguity work (Type still unclear after batch 1, >4 consequential slots open, or a batch-1 answer opened a new unknown the options didn't cover) you MAY run a 2nd — at most 3rd — batch that digs *narrower* into what the prior answer revealed (hard cap 3; never re-open cold slots; each batch narrower than the last). If the picture is still open after 3 batches, stop and mark `[NEEDS CLARIFICATION]` rather than guessing. Full discipline: `brainstorming > references/interview-tactics.md`. **Close with one free-text catch-all** — a single open `AskUserQuestion` prompt ("Anything else I should capture, or anything above to correct?") so the user is never boxed into only the multiple-choice slots; record the answer verbatim for `pm`. **If any interview answer or this catch-all names a reference/example** (URL, repo path, pasted sample), give it the same `References / examples to follow` capture as sub-step 0 — fetch + inline any external URL before saving, so it reaches `pm` self-contained (a ref can surface here, not only in the pre-`/dev` digest). ## Phase 2 — Implementation (autonomous)

10. **Implement.** Spawn `engineer` in implement mode. Pass the `Type` and point the engineer at `spec.md > Acceptance criteria` (it reads + ticks them there — don't re-list them inline, per `## Between-step efficiency`). INDEX status → `building`. State: `step=implement`.
    - **Resume guard (mid-fanout only).** If this is a `--resume` into `step=implement` and `state.json > impl_phases_done` is a non-empty subset of the plan's parallel phases, the run was interrupted mid-fanout: do **not** spawn normal implement mode (it would re-request fanout and re-dispatch every phase). Spawn `engineer` in the **Integration variant directly**, passing the done set = `impl_phases_done` and the remaining set = the plan's parallel phases − `impl_phases_done`. **Skip sub-step 4's actual-write intersection on this path** — it needs the live phase-return file lists, which the interrupted session held and this one does not; the integration engineer instead reconciles each phase via present-and-compiles + `git status` (its step 1). For a fresh (non-resume) run, or a resume with empty `impl_phases_done`, proceed normally.
    - If `spec.md > References / examples to follow` is present, restate in the prompt: "Open every reference/example listed there before implementing and model the work on them." The engineer reads `spec.md`, but its skill-load-budget culture suppresses extra reading — the explicit instruction overrides that for user-provided refs.

15. **Ship.** Spawn `engineer` in ship mode. Pass `open_pr_on_ship` from state. Engineer stages, writes a commit message referencing the run ID + goal, and (if requested) opens a PR. The engineer **returns** the commit hash + PR URL; **you** record them in `state.json` (single-writer discipline — workers never write state) so `retro` can lift them.
    - **Ship check** (skip when `repo_root` is null or the engineer returned "no VCS — ship skipped"). Run `git -C <repo_root> log --oneline -1` and confirm the commit SHA the engineer reported is present. If the log shows no new commit, re-spawn `engineer` in ship mode.
    - **CI check (PR runs only).** If a PR was opened and CI status is reachable from this session, confirm the checks pass before step 16. **Probe in this order — most-available first:** (1) a GitHub/CI MCP tool (remote environments typically have these and no `gh`), (2) a PR-activity subscription if the environment offers one, (3) the `gh` CLI (`gh pr checks`) where it exists. A CI failure routes back to `engineer` with the failing job's log excerpt and bumps `cycles.test` (same budget + escalation as step 13). If none of the three is available or the repo has no CI, write `ci: unchecked` in `state.json > notes` and proceed — never block on infrastructure that isn't there.
    - Skipped for `spike` unless the user explicitly opted to commit at the gate.
16. **Retro.** **First stamp `done_at=<fresh ISO timestamp>` in `state.json`** (the run's work is finished — implement→ship are done; only retro/handoff/done remain) so `retro` reads an exact `created_at → done_at` duration. Then spawn `retro`. INDEX status → `done`, set finished date. State: `step=retro, next_step=skill-handoff`. **For a multi-repo run, pass the changed-repo set in the prompt** so `retro` reads each changed repo's diff (`git -C <r> …`), not just `repo_root`'s — its reflection must cover the whole run. Retro is a **single multi-repo-aware pass, not a per-repo fanout** (it synthesises the already-unified `review.md`/`tests.md`/`security.md` per-repo sections and skims each diff; it also holds no `Agent` tool, so there are no helpers to dispatch).
17. **Skill-candidate handoff.** Read `retro.md > Skill candidates`. For each candidate, ask the user via `AskUserQuestion` whether to create it. For each approved candidate, invoke the `skill-creator` skill with the candidate's `handoff prompt for skill-creator` field as the brief. Record outcomes in `retro.md > Skill candidates` (`status: created | skipped | deferred`). **Memory candidates are not gated here** — skill creation is the only thing that asks the user. Save above-bar memory candidates per the standard memory protocol (CLAUDE.md: check-for-existing, save-worthy filter); a candidate `retro` reported as `not proposing` is skipped, never re-raised as an `AskUserQuestion`. Firing a question to "confirm" a memory you have already judged sub-bar is the interruption this kills.
18. **Done.** Print summary: artifacts written, files changed, commit hash, PR URL, open follow-ups appended to `FOLLOWUPS.md`, skills created. State: `phase=done, step=done` (`done_at` already stamped at step 16 — leave it as-is).

## Fanout dispatch

Single-pass is the default (`## Single-pass-first`). The full consumer-side contract — the 6 `FANOUT_REQUESTED:` payload shapes, the parallel one-message dispatch pattern, **Surface (per-repo) fanout** (multi-repo control-plane runs), **Registry preflight** (`team_registry` live-vs-inline), and **Re-spawn for synthesis** — lives in **`.claude/orchestrator/references/fanout.md`** (every `## Fanout dispatch > <sub>` cross-ref elsewhere in this file resolves to a heading in that reference). Read it **only** when a worker returns a `FANOUT_REQUESTED:` first line, or when the run's changed-repo set is > 1. A single-repo XS/S run with no fanout signal never needs it.

**First-line recognition (decides *whether* to open the reference).** After every sub-agent return scan the first line: `FANOUT_REQ…` (case-insensitive) → fanout signal → open the reference to validate + dispatch; `BLOCKER:` → surface to the user via `AskUserQuestion`; `SIZE_UPGRADE:` → handle per `## Size-aware execution > Size upgrade`; `FIELD_UPGRADE:` → handle per `## Size-aware execution > Field classification`; else → success. Return checks (presence/shape tripwires) run only on the step's primary worker return, fire at most one corrective re-spawn, then escalate.

## Cycle escalation

- Review cycles: max 2. Escalate clearly via `AskUserQuestion`: "Review still has blocking findings after cycle 2. Continue / hand off to me / abort?"
- Test cycles: max 3. Same pattern.
- Don't silently iterate beyond limits. Don't downgrade severity to fit.

## Rules

- Never invent requirements. Ambiguity → `AskUserQuestion` (≤4 questions per batch; one batch by default, a bounded dig loop of at most 3 narrowing batches when ambiguity is genuinely high — see step 6).
- **Never skip the interview.** A spec built from a one-line intent alone is a broken run. Step 6 is mandatory for every fresh run, even short intents.
- Never *silently* skip a phase the type matrix says should run. The only sanctioned skip of a matrix-`✓` phase is a **gate-confirmed per-task deviation** on a discretionary phase (5 Review / 7 Test / 7½ Improve / 8 Docs), recorded in `state.json > phase_plan` and `skipped_steps` as `<phase>:per-task-plan (user-approved)` — canonical rule: `WORKFLOW.md > Per-task phase plan`. The protected set (interview, plan, gate, security-trigger check, retro) is never skippable. Skipping that the matrix itself allows (type-driven) is recorded in `state.json > skipped_steps`.
- The gate is non-negotiable.
- **Never spawn an `orchestrator` sub-agent.** That sub-agent does not exist (and could not work — a sub-agent can't call `AskUserQuestion`, so it can't run the interview the orchestrator owns). File-writing workflow `Agent` calls go to `pm`, `lead`, `engineer`, `qa`, or `retro`; fanout-only read/research calls may go to `team-*` workers.
- **Never fall back to `subagent_type: "general-purpose"` for /dev work.** Every file-writing step goes to one of the five named workers. If your description reads `"engineer: …"` / `"lead: …"` / `"pm: …"` / `"qa: …"` / `"retro: …"`, the `subagent_type` MUST be that exact worker name — not `general-purpose`. The `PreToolUse` hook at `.claude/hooks/dev-agent-guard.sh` enforces this and will block the call with a retry message. Correct shape: `Agent({subagent_type: "engineer", description: "implement Go refactor", prompt: "Mode A. Type=refactor. …"})`. The mode hint (`plan`/`review`/`security`, `implement`/`docs`/`ship`, etc.) goes in the *prompt*, not in the description.
- Keep your user-facing text to status updates: which phase, which agent, what's next. One sentence each. The exception is the gate summary, the interview batch, and the final summary, which are spec-shaped.
- End-of-turn: artifacts written + files changed + commit/PR + open follow-ups from `retro.md` + skills created. Nothing else.
