# Init Project Docs (brownfield)

## Why this exists

Brownfield docs are only useful when they describe what exists, not a plausible system. This skill reads the actual code to produce a **fixed, predictable suite** — same eight topics every time — plus a `document.html` viewer (no server needed). The hard part is **accuracy**: read first, never invent — and when a suite already exists, reconcile rather than rubber-stamp.

## What it produces

All written into `docs/` (create it if absent):

| File | Topic | Required diagram |
|------|-------|------------------|
| `OVERVIEW.md` | What it is, who it's for, how to run it, repo layout | — |
| `ARCHITECTURE.md` | Components/modules, layering, boundaries, runtime data flow, integrations | mermaid `flowchart` / component diagram |
| `TECHSTACK.md` | Languages, frameworks, libraries, datastores, build/CI, versions, the *why* | — |
| `DATAMODEL.md` | Entities/tables/collections, fields, relationships, constraints | mermaid `erDiagram` |
| `COREFEATURE.md` | The handful of most important flows, end to end | mermaid `sequenceDiagram` **per flow** |
| `BUSINESSRULE.md` | Invariants, validation, policies, formulas, eligibility, state guards | optional mermaid `stateDiagram-v2` / `flowchart` |
| `API.md` | Endpoints, request/response, auth, errors | — |
| `DESIGN.md` | Design tokens, component inventory, screen/navigation map, key states, interaction & a11y patterns | mermaid `flowchart` (screen/navigation map) |
| `document.html` | Renders all the above (sidebar + mermaid) | generated by script |

`COREFEATURE.md` is the centrepiece (sequence diagram per core flow); `BUSINESSRULE.md` captures the rules the code enforces; `DESIGN.md` is produced only for a user-facing UI. Full per-file guidance: `references/workflow-and-quality.md > File-level guidance`.

## When to use / when to skip

**Use it** when there's existing code to document, onboard onto, or resync an existing suite against. This is brownfield work — the `understand` half of understand → lock → change, delivered as durable docs.

**Skip / adapt** when:
- **No code yet** (greenfield) — nothing to read, so this skill would invent. Design docs come from `plan-writing` / `brainstorming` instead.
- One **specific doc** for a narrow change, not a whole-project suite — write that directly.
- A doc's domain genuinely **doesn't exist** — no HTTP API, no datastore, no user-facing UI → no `DESIGN.md`, no real domain logic → no `BUSINESSRULE.md`. Don't pad it: write a one-line "Not applicable" stub, or drop the file entirely — the viewer adapts to whatever `.md` files are present.

## Two modes: fresh vs. update

First, check the target dir for an existing suite — any canonical file (`OVERVIEW.md`…`DESIGN.md`) or `document.html`:

- **Fresh** — none exists. Generate the whole suite.
- **Update** — a suite exists. Treat it as **input, not a blank slate**: re-ground against the code, revise in place with surgical diffs, and report the delta as a changelog.

Default to update when found; regenerate only if asked or unsalvageable (say so first). The grounding rule holds in both modes: **every surviving claim must still trace to code.**

## Workflow

Run in order — steps 1–2 are most of the value, never skip them. Full step detail: `references/workflow-and-quality.md`.

1. **Scope the repo** — manifests, entry points, top-level layout, config; fan out `Explore` / `team-codebase-explorer` agents for a large repo ([[fanout-team-agents]]). An existing `docs/` suite here means update mode.
2. **Understand before writing (the grounding rule)** — **every claim must trace to something you actually read**: TECHSTACK from manifests, DATAMODEL from migrations/schema, API from route definitions, COREFEATURE from traced call chains, BUSINESSRULE from validators/constants, DESIGN from frontend theme/component/router code. Say so when the code doesn't tell you; cite real anchors. Update mode: sort each claim keep / fix / add / remove — that four-bucket diff is the edit plan.
3. **Write (or update) the docs** — fresh: follow `references/doc-templates.md` skeletons, structure over prose, 3–6 core flows, one row per business rule, DESIGN only when a UI exists. Update: surgical edits from the four-bucket diff; preserve accurate human prose.
4. **Build the viewer** — `python3 .claude/skills/init-project-docs/scripts/build_doc_viewer.py --docs-dir docs --title "<Project Name>"`; never hand-write `document.html`; re-run after any `.md` edit (it's a snapshot).
5. **Self-review and report** — validate mermaid, re-run the script, report what was produced + honest unknowns; update mode leads with a changelog.

**Mermaid, Quality bar, Anti-patterns** — keep every diagram valid, every claim grounded, and every doc free of invented schemas, endpoints, or design systems; full checklists in `references/workflow-and-quality.md` (`> Mermaid: keep it valid`, `> Quality bar`, `> Anti-patterns`).
