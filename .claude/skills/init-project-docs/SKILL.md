# Init Project Docs (brownfield)

## Why this exists

Brownfield docs are only useful when they describe what exists, not a plausible-sounding system. This skill produces a **fixed, predictable documentation suite** by reading the actual code — same eight topics every time — plus a `document.html` viewer (no server needed). The hard part is **accuracy**: read the code first, refuse to invent — and when a suite already exists, re-read and reconcile rather than rubber-stamp.

## What it produces

All written into `docs/` (create it if absent):

| File | Topic | Required diagram |
|------|-------|------------------|
| `OVERVIEW.md` | What the project is, who it's for, how to run it, repo layout | — |
| `ARCHITECTURE.md` | Components/modules, layering, boundaries, runtime data flow, integrations | mermaid `flowchart` / component diagram |
| `TECHSTACK.md` | Languages, frameworks, libraries, datastores, build/CI, versions, the *why* | — |
| `DATAMODEL.md` | Entities/tables/collections, fields, relationships, constraints | mermaid `erDiagram` |
| `COREFEATURE.md` | The handful of most important user/runtime flows, end to end | mermaid `sequenceDiagram` **per flow** |
| `BUSINESSRULE.md` | The domain rules the code enforces: invariants, validation, policies, formulas, eligibility, state guards | optional mermaid `stateDiagram-v2` / `flowchart` |
| `API.md` | The published API surface: endpoints, request/response, auth, errors | — |
| `DESIGN.md` | The UX/UI surface: design tokens, component inventory, screen/navigation map, key states, interaction & a11y patterns | mermaid `flowchart` (screen/navigation map) |
| `document.html` | Self-contained viewer that renders all the above (sidebar + mermaid) | generated by script |

`COREFEATURE.md` is the centrepiece (sequence diagram per core flow); `BUSINESSRULE.md` captures the rules the code enforces; `DESIGN.md` is produced only for a user-facing UI. Full per-file guidance: `references/workflow-and-quality.md > File-level guidance`.

## When to use / when to skip

**Use it** when there is existing code to read and the user wants it documented, wants to onboard onto it, or wants an existing suite brought back in sync with the code. This is brownfield work — the `understand` half of the repo's understand → lock → change discipline, delivered as durable docs.

**Skip / adapt** when:
- There is **no code yet** (greenfield) — there is nothing to read; this skill would invent. Design docs come from `plan-writing` / `brainstorming` instead.
- The user wants **one specific doc** about a narrow change, not a whole-project suite — write that directly.
- A doc's domain genuinely **doesn't exist** (a CLI with no HTTP API, a stateless service with no datastore, a headless backend or library with no user-facing UI → no `DESIGN.md`, a thin CRUD/static project with no real domain logic → no `BUSINESSRULE.md`). Don't pad it — write a one-line "Not applicable: this project has no persistent datastore" and move on. An honest stub beats a fabricated schema or a design system that isn't there. (You may also drop the file entirely if the user prefers; the viewer adapts to whatever `.md` files are present.)

## Two modes: fresh vs. update

First, check the target dir for an existing suite — any canonical file (`OVERVIEW.md`…`DESIGN.md`) or `document.html`:

- **Fresh** — none exists. Generate the whole suite (default flow below).
- **Update** — a suite exists. Treat the docs as **input, not a blank slate**: re-ground against the code, then revise in place. Surgical diffs, not a rewrite. Report the delta as a changelog.

Default to update when a suite is found; regenerate only if the user asks or the docs are unsalvageable (say so first). The grounding rule (step 2) holds in both modes: **every surviving claim must still trace to code.**

## Workflow

Run in order — steps 1–2 are most of the value, never skip them. Full step detail: `references/workflow-and-quality.md`.

1. **Scope the repo** — manifests, entry points, top-level layout, config; fan out `Explore` / `team-codebase-explorer` agents for a large repo ([[fanout-team-agents]]). An existing `docs/` suite found here puts you in update mode.
2. **Understand before writing (the grounding rule)** — **every claim in every doc must trace to something you actually read**: TECHSTACK from manifests, DATAMODEL from migrations/schema, API from route definitions, COREFEATURE from traced call chains, BUSINESSRULE from validators/constants, DESIGN from the frontend theme/component/router code. Say so when the code doesn't tell you; cite real anchors. Update mode: sort every existing claim keep / fix / add / remove — that four-bucket diff is the edit plan.
3. **Write (or update) the docs** — fresh: follow `references/doc-templates.md` skeletons, structure over prose, 3–6 genuinely core flows, one row per business rule, DESIGN only when a UI exists. Update: surgical edits from the four-bucket diff; preserve accurate human prose.
4. **Build the viewer** — `python3 .claude/skills/init-project-docs/scripts/build_doc_viewer.py --docs-dir docs --title "<Project Name>"`; never hand-write `document.html`; re-run after any `.md` edit (it's a snapshot).
5. **Self-review and report** — validate mermaid, re-run the script, report what was produced + honest unknowns; update mode leads with a changelog (fixed / added / removed / kept).

**Mermaid** — a broken diagram is worse than none: fenced blocks, right diagram type per file, quote labels with punctuation, declare participants first, alphanumeric node ids. Rules + breakers: `references/workflow-and-quality.md > Mermaid: keep it valid`.

**Quality bar** — grounded, honest gaps, right files, diagrams render, skimmable, faithful delta (update), viewer built last, no secrets. Full checklist: `references/workflow-and-quality.md > Quality bar`.

**Anti-patterns** — documenting the framework not the project, invented schemas/endpoints/design systems, guessed diagrams, hand-written viewer, padded "Not applicable" filler, regenerating over human edits, leaving stale claims. Full list: `references/workflow-and-quality.md > Anti-patterns`.
