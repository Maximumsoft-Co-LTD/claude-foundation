# Orchestrator reference — Fanout dispatch

> Loaded on demand by the main agent (`.claude/orchestrator.md`). Open this only when a worker returns a `FANOUT_REQUESTED:` first line, or when the run's changed-repo set is > 1. A single-repo XS/S run with no fanout signal never needs it.

## Fanout dispatch

The `/dev` workflow's main agent and `pm`, `lead`, `qa`, and `engineer` sub-agents can request parallel team-agent fanout for the independent-sub-investigation case (spec research, plan integration points, review, security buckets, test categories, implement phases). The full pattern lives in `.claude/skills/fanout-team-agents/SKILL.md`; this section is the orchestrator's (main agent's) consumer-side contract.

**Direct nesting is the primary path (v2.1.172+).** The splittable agents (`pm`, `lead`, `qa`, `engineer`, and the self-splitting `team-*` workers) now hold `Agent` and **self-dispatch their helpers directly** — each carries a "Recruit help when the work is large" section. So a worker returning to you may already have run its own fanout. The `FANOUT_REQUESTED:` consumer contract below is the **fallback**: it handles the case where a worker prefers you to dispatch, and it remains the path for **background implement-fanout** (where phase-granular `state.json > impl_phases_done` resume is wanted). One exception where you still lead: **plan-prep push (step 8)** is the primary path for plan integration-point mapping — `lead` dedups against it.

**Prefer direct nesting for the read/research fanouts (plan / review / security / test) — it is cheaper.** The signal path costs a *double spawn*: the worker runs, returns `FANOUT_REQUESTED:`, you dispatch the team workers, then you **re-spawn the worker** to synthesise their findings. Direct nesting collapses that — the worker dispatches its own helpers and synthesises in place, no orchestrator re-spawn. So a fanout that looked too expensive to fire should fire **via direct nesting**, not be dropped to single-pass (the cost guardrail bites the signal path, not the work's independence). The `FANOUT_REQUESTED:` signal earns its keep for **background implement-fanout** (where phase-granular `impl_phases_done` resume is wanted) and as the **registry-fallback** path.

### Surface (per-repo) fanout — orchestrator-owned outer loop, no signal

The two fanout axes above split **one repo's** work: the *lens* axis (6 review workers / security buckets) and the *category* axis (test categories) both fan out within a single `repo_root`. A **control-plane run that spans multiple repos** adds a third, orthogonal axis: **surface** — split the three read-and-judge phases **review (step 11), security (step 12), and test (step 13)** **per repo** so N repos are read in parallel instead of one agent crawling them serially (the slow path the user hit). This is **never a `FANOUT_REQUESTED:` signal** — no sub-agent discovers it mid-work; **you (the orchestrator) already know the repo list at dispatch time** from `state.repos`, so you lead it directly — via **one Surface-coordinator spawn** that nests the per-repo helpers itself (see Dispatch) — exactly like plan-prep push. (**Retro (step 16)** is the fourth phase that reads across repos, but it is **multi-repo-aware single-pass, not surface-fanned** — it synthesises the already-unified per-repo artifact sections and holds no `Agent`, so there is nothing to parallelise; see step 16.)

The mechanics (full per-step detail in steps 11, 12, and 13; this is the shared contract):

- **When.** The run's changed-repo set (repos in `state.repos`, else `[repo_root]`, that this run actually changed) has size > 1. Size ≤ 1 → the single-repo path, unchanged. (Security additionally narrows to the subset of changed repos that trip sensitive paths — its *security-review set*.)
- **Dispatch (coordinator nests — foreground, no Case 3, no background).** Spawn **one** foreground `lead` (review or security) / `qa` (test) in its **Surface-coordinator variant**, passing the changed (or, for security, tripping) repo list. That coordinator **direct-nests one per-repo helper per repo itself** — `subagent_type="general-purpose"` carrying the agent's **Per-repo variant** contract inlined, scoped via `repo_root=<r>`, **foreground, all in one message** — then synthesises (next bullet). Helpers are `general-purpose` **on purpose**: a foreground same-message batch of the 5 /dev-worker types (`pm|lead|engineer|qa|retro`) self-blocks on the 2nd spawn under `dev-agent-guard.sh` Case 3 (the first return touches `.last_worker_return` before the next spawn's pre-check), so the helpers must run foreground but **not** be /dev-worker types — `general-purpose` falls through Case 3 entirely (PreToolUse waves it, PostToolUse marks nothing), exactly like the lens axis's `team-*`. This replaces the old orchestrator-direct **background** batch, which dodged Case 3 (background launches don't touch the marker — `dev-state-mark.sh`) but at two costs now retired: whether the harness reliably launches N background agents from one message was inferred-never-verified, and a background worker's state-discipline isn't hook-enforced (you had to hand-write `state.json` on each task notification). The orchestrator now makes only its **one** sequential coordinator spawn — the shape Case 3 is built for. **Cap 6** nested helpers; group beyond. (`lead`/`qa` can nest because they hold `Agent` — Claude Code v2.1.172+.)
- **No naive composition with the lens/category axes.** Per-repo reviewers/testers are **single-pass** by default — do not nest the 6-lens or per-category fanout inside each (that multiplies to 6×N agents). Reserve the inner axis for a single repo whose own diff is genuinely non-trivial, and keep the total within the concurrency cap.
- **Synthesis (same coordinator spawn — no re-spawn).** After its nested helpers return, the **same coordinator** writes the single unified `review.md`/`security.md`/`tests.md` with one `### Repo: <path>` subsection per repo plus the global anti-bias / AC-coverage walk (security aggregates `fix-required` iff any repo has a `high`) — dispatch and synthesis are now **one** spawn, not two, since the coordinator already holds every per-repo block it nested. Note `Dispatched-as: general-purpose` provenance in the artifact (the helpers carried the contract inlined — inline-fallback convention). **Aggregate verdict/status = pass/passing iff every repo passes.** **You** write `state.json` when the coordinator returns. The cycle counter (`cycles.review` / `cycles.test`; security high-loops bump `cycles.review`) bumps **once per fanout, per run** — never per repo. (Degradation: a coordinator that cannot nest — `Agent` unavailable / older Claude Code — reviews the repos **sequentially itself**, single-pass; correct, just serial.)
- **Coupled-change coherence (the one cross-repo check).** Surface fanout's premise is *separate trees, separate diffs, **zero shared state*** — true for an **independent** change (a sweep, or unrelated per-repo edits). A **coupled** multi-repo change — the changed repos share a contract this change touches (a proto/schema/IDL bump every service regenerates from, a shared client/server signature; the same *coupled* call `size-tiering.md` makes for sizing) — breaks that premise: each per-repo helper sees only its own repo and **cannot see a cross-repo skew** (repo A on contract v2.1, repo B still on v2.0). So on a coupled change the coordinator's **synthesis runs a cross-repo coherence check** — the shared contract (version, regenerated signatures, wire shape) must be consistent across **all** changed repos; a mismatch is **blocking**, the one defect no single per-repo block could surface. An independent change skips it (nothing shared to disagree). The same gap exists in test (per-repo suites pass on incompatible versions) — qa's synthesis confirms a cross-repo integration test covers the boundary.
- **Non-primary-repo findings dead-end (all three phases).** `engineer` and ship are scoped to the primary `repo_root`, so a blocking review finding, a failing test, or a `high` security finding in a **non-primary** repo has **no auto-fix path** — surface it to the user (`AskUserQuestion`) instead of routing to `engineer`, which would edit the wrong repo. Never downgrade a real `high` to fit the boundary.
- **Resume is fanout-granular, not per-repo.** Review, security, and test write no production code, so a mid-fanout `--resume` simply re-runs the whole per-repo batch. There is deliberately no `review_repos_done`/`security_repos_done`/`test_repos_done` analog to `impl_phases_done` — the per-phase resume machinery is only worth its complexity for implement, which mutates the tree.

Scope boundary (intentional): branch creation, implement, gate, and ship still operate on the single primary `repo_root`. Surface fanout parallelises only the **read-and-judge** phases (review / security / test) plus retro's multi-repo-aware read, which is safe because the diffs across repos already exist by the time those phases run. Full multi-repo targeting is a tracked follow-up (`FOLLOWUPS.md` F0001), not part of this axis.

### Recognising the signal

After every sub-agent return, scan the **first line** of the return: (a) case-insensitive `FANOUT_REQ` prefix → fanout signal (validate below); (b) `BLOCKER:` prefix → blocker (surface to user); (c) `SIZE_UPGRADE:` prefix → size upgrade (handle per `## Size-aware execution > Size upgrade`); (c′) `FIELD_UPGRADE:` prefix → field upgrade (handle per `## Size-aware execution > Field classification` — that paragraph is the canonical handler: record `field=brownfield` and backfill the understand/lock artifacts, routing each to its owner); (d) else → success. Before **advancing to the next step**, run the step's **Return check** if one is defined below. Return checks run **only** on the step's primary worker return (`pm` / `lead` / `engineer` / `qa` / `retro`) — **never** on intermediate `team-*` fanout workers, whose returns are collected for the synthesis re-spawn per `## Fanout dispatch` (the artifact doesn't exist until synthesis runs, so a check there would false-positive). A Return check is a presence/shape **tripwire**, not a quality review (that's the `lead` review and `qa` test gates) — it fires at most **one** corrective re-spawn; if the check still fails after that, escalate to the user via `AskUserQuestion` rather than looping. If a fanout signal is present, validate against the strict allowlist:

```text
^FANOUT_REQUESTED: (review|security:[a-z0-9,\-]+|plan:[a-z0-9,\-]+|test:[a-z0-9,\-]+|implement:[a-z0-9,\-]+|research:[a-z0-9,\-]+)$
```

If the first line matches the case-insensitive `FANOUT_REQ` prefix but does **not** match the strict regex (typos, casing, payload-shape errors), this is a **BLOCKER** — surface to the user via `AskUserQuestion` with the offending line and the 6 valid shapes. Do **not** silently fall through to non-fanout. The typo modes this catches: `FANOUTREQUESTED:` (missing underscore), `Fanout_Requested:` (case-mixed prefix), `FANOUT_REQUESTED:review` (no space after colon), `FANOUT_REQUESTED: REVIEW` (uppercase payload), `FANOUT_REQUESTED: review extra` (trailing junk), `FANOUT_REQUESTED: foo` (unknown payload).

### The 6 documented payload shapes

| Shape | Trigger phase / mode | Dispatch |
|-------|----------------------|----------|
| `FANOUT_REQUESTED: review` | Phase 2 step 11 — `lead` Mode B (**default** for a non-trivial diff: large, cross-module, critical, type/contract/test-sensitive, or uncertain; single-pass only for a small/low-risk diff) | Spawn the 6 review-focused `team-*` workers against the diff |
| `FANOUT_REQUESTED: security:<bucket-list>` | Phase 2 step 12 — `lead` Mode C (**default** when ≥ 2 buckets trip; single-pass for one bucket) | One `team-code-reviewer` per bucket with a focused threat-model prompt scoped to that bucket's paths |
| `FANOUT_REQUESTED: plan:<point-list>` | Phase 1 step 8 — `lead` Mode A (**default** for S/M/L existing-code work with independently-researchable points; single-pass for XS / pure-greenfield / one straightforward change) | For each point: one `team-codebase-explorer` pass for current state + one `team-best-practice-researcher` pass for current best practices — **but skip the `team-codebase-explorer` for any point the push-based plan-prep already mapped; re-dispatch only the residual `team-best-practice-researcher` (see step 8)** |
| `FANOUT_REQUESTED: test:<category-list>` | Phase 2 step 13 — `qa` (**default** when ≥ 2 of {unit, integration, e2e} AND any ≥ 3 tests) | One `team-pr-test-analyzer` per category |
| `FANOUT_REQUESTED: implement:<parallel-phase-list>` | Phase 2 step 10 — `engineer` Mode A (**feat-only**, default when the plan declares ≥ 2 `Parallelizable: yes` phases) | **Gate** on `Type==feat`, then **verify** the named phases' `Files touched (exclusive)` are pairwise-disjoint and every `Depends on` is `none` — refuse + fall back to single-pass engineer otherwise. Dispatch one **write-only** `engineer` (Parallel phase variant) per phase **background, one message** (`run_in_background: true` — `dev-state-mark.sh` skips the marker so no Case-3 self-block; write `state.json` + append `impl_phases_done` as each completion lands). Then foreground-spawn `engineer` in the **Integration variant** to wire shared glue + install deps + run every `verify:` + tick ACs. Resume is **phase-granular** (`impl_phases_done`), not sub-step — a mid-phase interrupt re-runs that phase. |
| `FANOUT_REQUESTED: research:<question-list>` | Phase 1 step 7 — `pm` return-signal, plus step 6 spec-prep fanout from the main agent | One `team-codebase-explorer` per `codebase-*` question and one `team-best-practice-researcher` per `best-practice-*` question. pm cannot dispatch directly — pm returns `FANOUT_REQUESTED: research:<…>` **after writing a draft `spec.md`** (draft-first); orchestrator dispatches, then re-spawns pm to **read its own draft `spec.md`** (digest/Q&A already folded in) plus the findings and refine in place — see step 7. |

### The dispatch pattern (parallelism)

Once the signal validates, dispatch **all workers in the same orchestrator message** — Claude Code's `Agent` tool runs them concurrently when multiple invocations appear in one assistant turn. Sequential `Agent` calls across multiple turns are **not** parallel.

```
# In one orchestrator message — example: the review fanout's 6 workers:
Agent(subagent_type="team-code-reviewer",            description="...", prompt=<focused-prompt-1>)
Agent(subagent_type="team-code-simplifier",          description="...", prompt=<focused-prompt-2>)
Agent(subagent_type="team-comment-analyzer",         description="...", prompt=<focused-prompt-3>)
Agent(subagent_type="team-pr-test-analyzer",         description="...", prompt=<focused-prompt-4>)
Agent(subagent_type="team-silent-failure-hunter",    description="...", prompt=<focused-prompt-5>)
Agent(subagent_type="team-type-design-analyzer",     description="...", prompt=<focused-prompt-6>)
```

Each shape dispatches **its own worker set** (the table above is authoritative) — e.g. `plan:<point-list>` sends one `team-codebase-explorer` + one `team-best-practice-researcher` per point, never the review six. The one-message rule applies to every shape.

Each prompt is **self-contained** (the workers inherit none of the calling sub-agent's context). Include scope (paths / diff slice), goal (one sentence), constraints (what NOT to do), and output shape (the worker's documented section format from `.claude/agents/team-<role>.md`).

### Registry preflight — decide once, record, thread

The `team-*` registry is **session-scoped**: `team-*.md` files created mid-session (and edits to an existing agent's `.md`) are not discoverable until a session restart, so a `team-<role>` spawn can fail with `Agent type 'team-<role>' not found`. Handle this **once per run — like the no-git decision (step 2)**: decide the path, record it, reuse it, and **never let a `not found` make you retreat to single-pass** (that silent retreat is the #1 cause of "I didn't see fanout help").

- **The first `team-*` dispatch of the run is the probe.** Record the outcome in `state.json > team_registry`: `"live"` if the spawn resolves, `"inline-fallback"` if it returns `Agent type ... not found`. Every later fanout — yours or a self-dispatching worker's — reads this field and uses the recorded path **without re-probing**. (No fanout ever fires → it stays `null`, which is fine.)
- **On `inline-fallback`, reissue inline — do NOT drop the fanout.** Re-issue every worker spawn with `subagent_type="general-purpose"` and the worker's role contract read inline into the prompt (read `.claude/agents/team-<role>.md` end-to-end, prepend it to the focused prompt). Parallelism is preserved (one message, N `Agent(...)` calls). Record the actual `subagent_type` per spawn for the synthesis `Dispatched-as:` map. **Single-pass is never the response to a registry miss** — the work is still independent; only the spawn mechanism changed.
- **Thread it into splittable-worker prompts, and capture what they report back.** Every `pm`/`lead`/`qa` spawn (these self-dispatch `team-*` helpers) carries a `team_registry: <live|inline-fallback|unknown>` line so the worker self-dispatches via the known path. (`engineer`'s implement-fanout helpers are `engineer`-type — always in the registry — so they are **registry-exempt**; pass `team_registry` to `engineer` only when its build may recruit read-only `team-*` research helpers.) If `team_registry` is still `unknown` (no fanout has fired yet) the worker attempts `team-*`, falls to inline on `not found`, and **reports the path it used as a line in its return** (e.g. `team-registry: inline-fallback`). **Orchestrator action (closes the loop):** on any worker return carrying such a line while `state.json > team_registry` is still `null`/`unknown`, write that reported value to `team_registry` before spawning the next step — the probe then happens at most once per run.
- **Session restart is the other fix** (close/reopen so the registry refreshes — the user's action). Inside a run, the inline path keeps fanout firing without it. Full caveat: `.claude/skills/fanout-team-agents/SKILL.md > Operational caveats > Agent registry is session-scoped`.

### Re-spawn for synthesis

When every worker returns, re-spawn the calling sub-agent (`pm` / `lead` / `qa` / `engineer`) with:

- The workers' outputs concatenated into the prompt (one labelled block per worker).
- A `Dispatched-as:` map: one line per worker, `team-<role> → <actual subagent_type that ran>` (so the calling sub-agent can fill the mandatory `**Dispatched-as**:` provenance line on each `### team-<role>` subsection of the artifact — see `.workflow/_templates/review.md > Per-agent findings`).
- **Re-include any prompt-only context the first spawn carried**, because the re-spawned sub-agent inherits none of it — but prefer durable artifacts over prompt re-passing. For `pm` nothing requirement-bearing is re-passed: pm wrote a draft `spec.md` first (draft-first) and re-reads it (digest/Q&A folded in), so the re-spawn only carries the worker findings. For `lead` / `qa` / `engineer` the inputs they read from disk (`spec.md` / `plan.md` / diff) already carry the requirements, so only re-pass genuinely prompt-only context (e.g. review findings being addressed).

The re-spawned sub-agent does the synthesis (spec discovery notes; plan current-state / research notes; per-agent sections + its own plan-adherence / AC / coverage / integration pass).

### Where fanout fires

**Every fanout point that fires, as it runs, does three things:** (a) **honours any gated `state.json > fanout_plan.<phase>`** (the gate-steerable phases only — `review`/`security`/`test`/`implement`) — `off` → single-pass, `on` → fan out past the runtime cost heuristic, subject to the hard feasibility guardrails **and the size-tier machinery** (a forced `fanout review on` on an XS/S run, where the tier refuses review-fanout, becomes a `SIZE_UPGRADE` prompt, not a silent honour); absent an entry, the step's own heuristic below decides; (b) **prefers direct nesting** (the worker self-dispatches, no re-spawn) over the `FANOUT_REQUESTED:` signal for the read/research fanouts; (c) **appends one `state.json > fanout_log` entry** `{phase, eligible, fired, path, n, reason}` keyed by **phase name** (`path` ∈ `direct`/`signal`/`single`) **in that step's terminal `state.json` write — re-read the array and append, never regenerate from memory (same array discipline as `impl_phases_done`)**. The log is **broader than the gated plan**: it records *every* fanout point — `spec-prep` (step 6) and `plan` (step 8) run before the gate and carry no `fanout_plan` key, plus the four gate-steerable Phase-2 phases — so `retro` can surface whether each eligible phase actually fanned out (and any gated-intent-vs-actual divergence), turning "I didn't see fanout fire" into a measurable finding rather than a vibe.

The steps that can fire a fanout (signal originated by the main agent or spawned sub-agent, dispatched here):

- **Step 6 — Spec prep** — **opt-in** (per `## Single-pass-first`): main agent runs the interview off its own read by default; dispatches `team-codebase-explorer` / `team-best-practice-researcher` before the interview only when 2+ of {existing code named, integration points, APIs, security-sensitive paths, unfamiliar domain terms, 2+ independent research questions} hold and the research is substantial. Always single-pass for XS/S and pure-greenfield work.
- **Step 7 — Spec** — `pm` may return `FANOUT_REQUESTED: research:<question-list>` if it needs codebase or best-practice probes before writing `spec.md`.
- **Step 8 — Plan** — two paths. **(a) Push-based plan-prep (preferred for speed):** before the `lead` spawn, the orchestrator dispatches one `team-codebase-explorer` (haiku) per integration point in parallel for M/L existing-code work with ≥ 2 integration points, then spawns `lead` once with the findings — this keeps the slow LSP-walk off `lead`'s critical path. **(b) Pull-based fallback:** `lead` Mode A may still return `FANOUT_REQUESTED: plan:<point-list>` for anything prep did not cover (typically best-practice research); the orchestrator dispatches the residual workers and re-spawns `lead`.
- **Step 10 — Implement** — `engineer` returns `FANOUT_REQUESTED: implement:<parallel-phase-list>` by default when the plan declares ≥ 2 `Parallelizable: yes` phases (**feat-only**). Orchestrator gates on `feat`, verifies the exclusive Files-touched are pairwise-disjoint, dispatches write-only phase-engineers in the background, then a foreground integration engineer; see the table row + step 10 contract above.
- **Step 11 — Review** — `lead` Mode B returns `FANOUT_REQUESTED: review` by default for a non-trivial diff (deserves independent specialist passes); it writes `review.md` directly only for a small/low-risk diff.
- **Step 12 — Security review** — `lead` Mode C returns `FANOUT_REQUESTED: security:<bucket-list>` by default when ≥ 2 buckets trip (single-pass for one bucket).
- **Step 13 — Test** — `qa` returns `FANOUT_REQUESTED: test:<category-list>` by default when the suite splits (≥ 2 categories AND any ≥ 3 tests).
