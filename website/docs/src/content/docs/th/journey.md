**ผู้อ่าน:** ผู้ใช้โปรเจกต์ อ่านหน้านี้หลัง [Change Loop คืออะไร](/docs/th/) และก่อนติดตั้ง เพื่อให้เห็นว่าการทำ change เป็นอย่างไร ขั้นตอนติดตั้งจะได้เข้าใจง่ายขึ้น

change หนึ่งงานผ่านห้าขั้นตอน งานส่วนใหญ่เป็นของ coding agent และ harness
**คุณปรากฏตัวแค่สามจังหวะ** คืออนุมัติข้อตกลง ตรวจผลลัพธ์ และอนุญาต Land

![ห้าขั้นของ lifecycle สิ่งที่แต่ละขั้นให้ ผู้ลงมือ และเส้นทางย้อนกลับเมื่อ requirement เปลี่ยน](/docs/diagrams/loop-th.svg)

## ใครทำอะไร ทีละขั้น

![swimlane ของ คุณ, Agent และ Harness ข้ามขั้น Investigate, Change, Build, Prove และ Land ช่องสีส้มคือจังหวะที่ต้องการคุณ](/docs/diagrams/journey-th.svg)

ช่องสีส้มคืองานทั้งหมดของคุณ agent เขียนและซ่อม ส่วน harness แยกพื้นที่
รันเครื่องมือของโปรเจกต์ บันทึกหลักฐาน และนำผลเข้าโปรเจกต์

## ตัวอย่างจริง

เป้าหมาย: ให้เจ้าของบัญชีแก้ display name ของตัวเองได้ ทุกบรรทัดด้านล่างคือสิ่งที่คุณพิมพ์
หรือสิ่งที่คุณเห็น ส่วนคำสั่งระหว่างทางเป็นของ agent

| # | คุณ | สิ่งที่เกิดขึ้น | สิ่งที่คุณเห็น |
|---|---|---|---|
| 1 | `/change allow an account owner to edit their display name` | agent ศึกษาพฤติกรรมเดิมและร่างข้อตกลง harness compile และตรวจให้ | คำถามขออนุมัติพร้อมแพ็กเกจที่อ่านง่าย: ขอบเขต scenario ความเสี่ยง และวิธีตรวจผล |
| 2 | อ่าน scenario แก้สิ่งที่ผิด ("ชื่อมี emoji ได้") แล้ว**อนุมัติ** | agent แก้ draft ยังไม่มีการสร้างโค้ด | change ID เดิม พร้อมการแก้ที่รวมอยู่ในข้อตกลง |
| 3 | `/build <change-id>` | agent เขียนโค้ดและเทสใน workspace ที่แยกไว้ harness คุมขอบเขตและงบ | ความคืบหน้า และคำถามเฉพาะเมื่อมี trade-off จริง |
| 4 | ไม่ต้องทำอะไร (Build ไหลต่อเข้า Prove) | harness รันเทส linter และ browser check เก็บ receipt ต่อ claim และรันซ้ำเฉพาะสิ่งที่การแก้ทำให้ stale | สรุปผล: ผ่าน ไม่ผ่าน หรือ *ตรวจไม่ได้* ซึ่งไม่เคยนับว่าผ่าน |
| 5 | ตรวจสรุปและ diff | agent ซ่อมสิ่งที่พบเป็นชุดเดียวตามลำดับ | สถานะ `proven` — พร้อมแล้ว แต่ **ยังไม่ส่งมอบ** |
| 6 | `/land <change-id>` | harness นำงานที่ proven เข้าโปรเจกต์ครั้งเดียว sync spec, archive และเก็บกวาด | สถานะ `archived`: diff อยู่ในโปรเจกต์แล้ว แต่ **ยังไม่ commit** |

จากนั้นคุณ commit, push หรือเปิด PR ตามกระบวนการเดิม หรือใช้ [`/deliver`](/docs/th/cli/)
ที่เป็นทางเลือกและต้องมีสิทธิ์ของตัวเอง

:::tip[เสร็จ คือ `archived`]
`proven` แปลว่าหลักฐานดี แต่มีเพียง `archived` ที่แปลว่าโค้ดถูกส่งมอบแล้ว
Land ไม่เคย commit, push หรือเปิด pull request เอง
:::

## สถานการณ์อื่นที่จะเจอ

| สถานการณ์ | ต้องทำอะไร | ทำไมจึงปลอดภัย |
|---|---|---|
| ยังไม่รู้สาเหตุหรือพฤติกรรมที่ถูกต้อง | เริ่มด้วย `/investigate <คำถาม>` | อ่านอย่างเดียว ผลที่ได้ส่งต่อให้ `/change` |
| requirement เปลี่ยนระหว่าง build | บอก agent และใช้ change ID **เดิม** | agent แก้ข้อตกลงและยกเลิกเฉพาะ proof ที่ stale |
| check ไม่ผ่าน | อ่านทางเลือกที่ agent เสนอ: ทำต่อ พัก หรือ waive | waive คือการตัดสินใจที่บันทึกไว้ ไม่เคยเปลี่ยนความล้มเหลวให้เป็นผ่าน |
| session หรือ Land ถูกขัดจังหวะ | ขอให้ agent ทำต่อ ใช้ `/changes` ดูสถานะ | state อยู่ในไฟล์ ไม่ใช่ในแชต อย่าสร้าง change ใหม่หรือแก้ runtime record เอง |
| งานครอบคลุมหลาย repository | ประกาศขอบเขตก่อน ดู [หลาย repository](/docs/th/multi-repository/) | หนึ่ง change หนึ่ง proof หนึ่ง Land ข้ามทุก repository |

## ไปต่อที่ไหน

1. [ติดตั้ง](/docs/th/install/) — ไม่กี่นาที ทำครั้งเดียวต่อโปรเจกต์
2. [เริ่มใช้งาน](/docs/th/quickstart/) — ลอง flow เดียวกันนี้กับโปรเจกต์ของคุณ
3. [การอนุมัติโดยคน](/docs/th/approval/) — สิ่งที่คุณต้องอนุมัติ และสิ่งที่ปล่อยให้ agent ได้อย่างปลอดภัย
