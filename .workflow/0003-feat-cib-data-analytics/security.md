# Security review: CIB data analytics webapp

**Plan**: [./plan.md](./plan.md)
**Reviewed**: 2026-05-21
**Trigger**: sql (case_repo dynamic WHERE) + path/file (xlsx multipart upload + BYTEA storage + excelize parse) + html (markdown notes via react-markdown + rehype-sanitize) + secrets (`.env.example` defaults + orphan PuppyGraph creds) + network (new unauthenticated HTTP API + permissive CORS `*` + `0.0.0.0` bind) + deserialise (JSON `Decode` on every handler + xlsx blob parse on attacker-controlled bytes)
**Verdict**: pass

## Threat model

The v1 system is explicitly unauthenticated (spec non-goal: "no auth in v1") and the Go server in `cmd/api/main.go:88` binds `:8080` — i.e. all interfaces — so the operative threat model is: **any actor who can route a TCP packet to the host's :8080 (and :3000 for the Next.js shell)** has full, unauthenticated CRUD on cases, files, and graphs. On a developer's laptop with localhost-only docker networking the blast radius is the developer; on any networked host (LAN VM, internal staging, a curious cloud VM whose security group "just for now" allows 8080), the blast radius is anyone who can reach those ports. The CORS middleware (`router.go:50-61`) sets `Access-Control-Allow-Origin: *` so a victim analyst's browser can also be steered into firing requests against a colleague's running instance from any drive-by web page. Trust boundaries crossed by this diff: (1) **internet/LAN → API** (no authn, no rate limit, no origin allowlist); (2) **multipart upload → excelize parser → Postgres BYTEA** (attacker controls the bytes that `excelize.OpenReader` decompresses, and the bytes that land in `original_blob`); (3) **user markdown notes → DOM** (rendered by `react-markdown` with `rehype-sanitize` default schema, no `rehype-raw`, so raw `<script>` is rendered as text — safe); (4) **case-filter query params → dynamic SQL** (`case_repo.go:62-95` uses parameterised pgx placeholders for every user-controlled fragment — safe). The realistic adversary is an opportunistic scanner or a malicious browser tab; the dangerous-realistic outcome is **either resource exhaustion via a hand-crafted xlsx zip-bomb that `excelize.OpenReader` decompresses with no size cap, or remote tampering of an investigator's case data via the unauthenticated API.** Data sensitivity at runtime is high (real CIB use case = bank/crypto/phone/travel records of real people) even though no real data ships in the repo.

## Checklist

### Input handling

- [✓] All user input validated at the boundary, not deep inside — `excelize_adapter.go:50-77` validates `ColumnMapping.Validate` against parsed headers before any row processing; `upload_file.go:35-46` rejects empty/too-large/wrong-extension at the use-case boundary; `cases.go:79-102` parses query params into typed `CaseFilters` at the handler.
- [✓] No string concatenation into SQL / shell / HTML / paths — `case_repo.go:62-95` uses pgx placeholders (`$1`, `$2`, ...) exclusively; the `strconv.Itoa(idx)` builds the placeholder number, not the user value (user values go through `args = append(args, ...)`). `file_repo.go`, `graph_repo.go`, `mapping_tx_writer.go` are all parameterised. No `fmt.Sprintf` into SQL, no shell exec, no `dangerouslySetInnerHTML` in React.
- [✗] Parser/decoder choice safe for untrusted input — `excelize.OpenReader` (`excelize_adapter.go:24, 54`) is invoked with **no `excelize.Options{UnzipSizeLimit, UnzipXMLSizeLimit}`**, so a 5 MiB xlsx that decompresses to multi-GB shared-strings.xml is uncapped by the parser. The outer `http.MaxBytesReader` (`files.go:46`) only bounds the compressed bytes. This is a zip-bomb amplification vector. Severity: medium (see Findings).

### Authn / authz

- [N/A] Every new endpoint has an explicit authz check — **by spec** there is no authn/authz in v1 (`spec.md > Out`: "No authentication, login, RBAC, or multi-user collaboration in v1"). Every endpoint is wide-open by design. The non-blocking carry-forward is: when v2 lands, this row flips from N/A to a hard requirement, and the v1 deploy story (`0.0.0.0` bind + CORS `*`) must be re-evaluated.
- [N/A] Session/token storage is httpOnly + secure + SameSite — no sessions exist in v1.
- [N/A] No new "admin" code path skips the existing authz layer — no authz layer exists yet.

### Secrets + crypto

- [~] No hard-coded secrets, API keys, or test credentials in the diff — `app/.env.example:1-2` `POSTGRES_USER=cib` / `POSTGRES_PASSWORD=cib` and `:15-16` `PUPPYGRAPH_USER=puppygraph` / `PUPPYGRAPH_PASSWORD=puppygraph123` are **example/default credentials**, which is the *intended* shape of `.env.example`. **However**, `cmd/api/main.go:34` falls back to `postgres://cib:cib@localhost:5432/cib?sslmode=disable` when `DATABASE_URL` is unset — i.e. the binary will silently boot with weak default creds and SSL disabled if the operator forgets `.env`. Severity: low (see Findings). The `PUPPYGRAPH_*` vars are also dead post-B8 (cycle-2 review carry) but the password-shaped string remains in the example file.
- [✓] No custom crypto — `sha256.Sum256` on the file blob (`upload_file.go:52`) via the stdlib. No homegrown anything.
- [N/A] PRNG used for security purposes is a CSPRNG — no security-sensitive PRNG use; `uuid.New()` (google/uuid) is v4 CSPRNG-backed; not used for auth.

### Output / rendering

- [✓] Untrusted text escaped on the way out — case notes go through `MarkdownView.tsx` which composes `react-markdown` + `rehype-sanitize` (default schema) + `remark-gfm`; no `rehype-raw`, so raw `<script>` / `<iframe>` in notes are rendered as literal text. Filename (`header.Filename`, attacker-controlled) is rendered through React text children only — `FileToggleList.tsx:22` and `NodeDetailPanel.tsx:87` — which auto-escape. JSON response bodies use `json.NewEncoder` (`files.go:80,127,165,173` etc.), which escapes per RFC 8259. `Content-Disposition` filename in `graph.go:81` uses the caseID UUID (not user input) — no header-injection vector.
- [N/A] Redirect targets validated against an allowlist — no server-side redirects in the diff. `/` → `/cases` is a Next.js client-side redirect to a static path.
- [✗] Error messages don't leak stack traces / internal paths — `middleware/errors.go:42` maps unknown errors to `"internal error"` + 500 (good), **but** several handlers wrap raw errors in `WriteError(w, err)` where `err` is a `json.Decoder` or `uuid.Parse` error and the body will echo `err.Error()` via `domain.ErrCaseNotFound`-style fallthrough — see cycle-2 review's silent-failure carry #6 + #7 (`handlers/files.go:153,187` JSON decode → opaque 500; `handlers/{files,graph,cases}.go` `uuid.Parse` → 500). The leakage is bounded (Go's `json.Decoder` errors say e.g. `"invalid character 'x' looking for value"`, not paths) — but it's worth tightening. Severity: low (see Findings).

### Infra-adjacent

- [N/A] File path joins go through `path.join` / `filepath.Clean` and reject `..` — files are stored as `BYTEA` in Postgres (`migrations/0003_create_files.sql:7`), not on disk. There is no filesystem path joining anywhere in the upload flow. `header.Filename` is metadata only.
- [✗] New outbound network call has a timeout and a target allowlist — there are no outbound HTTP calls in the diff (the Go server is purely inbound). **Inbound** posture is the concern: `:8080` bind on all interfaces + permissive `CORS *` + no rate limit + no security headers (no CSP, no X-Content-Type-Options, no X-Frame-Options, no Referrer-Policy). Severity: medium for the CORS `*` (see Findings); the bind-address is a v1-deploy footgun (see Findings).
- [✓] New process exec doesn't shell out with user input — no `os/exec` in the diff. The smoke script (`app/scripts/smoke.sh`) is operator-run, not driven by user input.

## Findings

### Blocking (severity = high)

**None.** The dominant risk surface is the no-auth + open-bind + CORS `*` posture, which is explicitly spec'd as a v1 non-goal. Treating that as `high` here would override the spec. The xlsx zip-bomb is real but mitigated by the 5 MiB outer cap (an attacker has to spend serious compression to make 5 MiB hurt — feasible but requires deliberate crafting against an unauthenticated endpoint; combined with no rate limit it's medium-grade DoS, not RCE/data-loss). No injection, no RCE, no auth-bypass found.

### Non-blocking (severity = medium / low)

**Medium**:

- `app/backend/internal/adapters/driven/xlsx/excelize_adapter.go:24,54` — `excelize.OpenReader(bytes.NewReader(blob))` is called with no `excelize.Options{UnzipSizeLimit, UnzipXMLSizeLimit}`. A 5 MiB xlsx whose `xl/sharedStrings.xml` decompresses to multi-GB will exhaust the API container's memory (xlsx is a zip; excelize defaults to no decompression cap). **Fix**: switch to `excelize.OpenReader(blob, excelize.Options{UnzipSizeLimit: 50*1024*1024, UnzipXMLSizeLimit: 50*1024*1024})` (or your chosen cap), and surface a new `ErrXlsxTooComplex` sentinel mapped to 413 in `middleware/errors.go`. Combined with the lack of rate limiting on the upload endpoint, this is a DoS-only vector — but a cheap one to harden.

- `app/backend/internal/adapters/driving/http/router.go:52` — `Access-Control-Allow-Origin: *` is set for all routes, including the data-mutating endpoints (`POST /api/v1/cases`, `PATCH /api/v1/cases/:id`, `POST /api/v1/cases/:id/files`, etc.). With `*` and the v1 no-auth posture, *any web page* the analyst visits can fire mutating requests at a running localhost API in their browser. Browsers refuse `Allow-Origin: *` with credentials, so cookies aren't sent — but there are no cookies in v1 (no auth), so the attacker doesn't *need* credentials; the request just lands and succeeds. **Fix for v1**: tighten to `Access-Control-Allow-Origin: http://localhost:3000` (i.e. only the Next.js shell). When v2 auth lands, revisit alongside the cookie/SameSite story.

- `app/backend/cmd/api/main.go:88` — `Addr: ":" + port` binds to `0.0.0.0:8080`. With no auth, anyone on the same network (coworker on the same Wi-Fi, anyone on the same cloud VPC subnet, anyone whose laptop is on a coffee-shop network) can hit the API. **Fix for v1**: bind to `127.0.0.1:` + port by default, and gate the all-interfaces bind behind an explicit `API_BIND=0.0.0.0:8080` env var that the README documents as "only set this when you understand the auth posture." The docker-compose port-publish (`docker-compose.yml:25`) does its own bridging; binding the in-container process to `0.0.0.0` is only needed because docker's port-publish requires it — that's a known docker workaround, so the right fix here is to bind to all-interfaces *only* when running inside docker, and add the warning in the README.

**Low**:

- `app/backend/cmd/api/main.go:34` — `dsn := os.Getenv("DATABASE_URL"); if dsn == "" { dsn = "postgres://cib:cib@localhost:5432/cib?sslmode=disable" }`. The fallback ships weak default creds (`cib:cib`) and `sslmode=disable` baked into the binary. If the operator forgets to set `DATABASE_URL` the API will silently boot against a default-credentials, plaintext-traffic Postgres on localhost. **Fix**: fail fast — log `database_url.missing` and `os.Exit(1)` when `DATABASE_URL` is unset, instead of falling back. The dev-defaults belong in `.env.example`, not in the binary.

- `app/.env.example:1-2,15-16` — example file ships `POSTGRES_PASSWORD=cib` and `PUPPYGRAPH_PASSWORD=puppygraph123`. The `puppygraph123` string is dead post-B8 (cycle-2 carry, retro item) but if an operator copies `.env.example` to `.env` and ships it, they get `cib:cib` Postgres creds in production. **Fix**: replace the password values in `.env.example` with `__change_me__` placeholders and document the swap in `app/README.md`. Drop the `PUPPYGRAPH_*` rows entirely (cycle-2 retro item).

- `app/backend/internal/adapters/driving/http/handlers/files.go:153,187` (and `cases.go:65,145`, `graph.go` parses) — `json.NewDecoder(r.Body).Decode(&req)` errors are forwarded straight to `middleware.WriteError`, which falls through to `"internal error"` + 500. This is silent-failure carry #6 from cycle-2 review.md. The body of a JSON parse error doesn't leak filesystem paths (Go's encoder returns shape-of-input errors like `invalid character 'x' looking for value`), so this is low-severity from a leakage angle — but it does invite scanners to probe (a 500 on bad JSON looks more interesting than a 400). **Fix**: map `*json.SyntaxError` / `*json.UnmarshalTypeError` / `io.ErrUnexpectedEOF` to 400 with a fixed `"invalid request body"` message in `middleware/errors.go`. Same treatment for `uuid.Parse` errors (silent-failure carry #7).

- `app/backend/internal/adapters/driving/http/handlers/{cases,graph,files}.go` — JSON endpoints have **no `http.MaxBytesReader` body cap**. The upload endpoint correctly caps multipart at 6 MiB (`files.go:33,46`), but `POST /api/v1/cases` and `PATCH /api/v1/cases/:id` will happily `json.Decode` a body of any size. `json.Decoder` does stream, so memory usage is bounded — but a slow-loris client can hold a goroutine open. Combined with no rate limit, this is a small DoS amplifier. **Fix**: wrap every handler body with `http.MaxBytesReader(w, r.Body, 256 * 1024)` (256 KiB is generous for the largest legitimate payload — a case PATCH).

- `app/backend/internal/adapters/driving/http/router.go` — no security headers anywhere: no `X-Content-Type-Options: nosniff`, no `X-Frame-Options: DENY`, no `Referrer-Policy: no-referrer`, no `Content-Security-Policy` on the Next.js side either. None of these are exploitable on their own in v1, but they're free defense-in-depth. **Fix**: add a `securityHeaders` middleware to the chi router with the four headers above; configure `Content-Security-Policy` on Next.js via `next.config.js` headers.

- `app/backend/internal/adapters/driving/http/router.go` — no rate limiting. Combined with the no-auth posture, an attacker can fire unlimited xlsx-uploads (each up to 5 MiB) at the upload endpoint. **Fix**: add a per-IP token-bucket on `POST /api/v1/cases/:id/files` (e.g. 10 uploads / minute / IP) using `chi/middleware.Throttle` or `ulule/limiter`.

- `app/backend/internal/adapters/driving/http/handlers/files.go:46-56` — the 6 MiB `MaxMultipartBytes` cap is right, but if the cap is *hit*, `ParseMultipartForm` may have already buffered up to 32 MiB by default (Go's `mime/multipart` defaultMaxMemory). The MaxBytesReader truncates the *body*, so the buffer is bounded by the body — this is actually fine. Note for completeness; no change needed.

- `app/backend/internal/adapters/driven/postgres/case_repo.go:67-68` — `ILIKE '%' || $1 || '%'` (or equivalent — the code uses Go-side `"%"+f.TitleSubstring+"%"` and passes as `$1`) is safe from SQLi (parameter is bound) but is vulnerable to **ReDoS-style cost amplification** if `TitleSubstring` contains many wildcard characters (`%`, `_`). Postgres treats `%` and `_` in the *bound value* as wildcards in `ILIKE`. A pathological query like `%_%_%_%_%_%` against a large table can degrade. v1 has no `cases` row at scale yet, so the impact is theoretical. **Fix when scale arrives**: `escape(TitleSubstring, `\\`)` to escape `%` and `_` in user input, or switch to `websearch_to_tsquery` against a fulltext index.

- `app/backend/internal/adapters/driven/postgres/tx.go:16` — `_ = tx.Rollback(ctx)` discards rollback errors. Cycle-2 review carry. Not a confidentiality/integrity issue but it hides connection-pool corruption from operators. **Fix**: log at `Warn` if `tx.Rollback` returns an error that isn't `pgx.ErrTxClosed`.

- `app/backend/internal/adapters/driven/postgres/mapping_tx_writer.go:22-27` — `ON CONFLICT (file_id) DO UPDATE` on `file_graphs` silently overwrites a prior parse. If an attacker (or a confused analyst) re-parses with a different mapping, the prior graph is gone — no audit trail. Cycle-2 silent-failure carry #5. **Fix**: add a `file_graphs_history` table or an `audit_log` row on overwrite.

- `app/backend/internal/adapters/driven/postgres/migrations/0003_create_files.sql:6` — `original_blob bytea NOT NULL`. Storing the raw upload bytes in the DB means a malicious xlsx now sits in Postgres until the case is deleted (cascading delete via FK is in place — `:5`). For real CIB data, that blob is highly sensitive. v1 has no at-rest encryption story (`sslmode=disable` in the default DSN doesn't help, but that's transport not at-rest). **Fix for v2**: encrypt the blob column with `pgcrypto`'s `pgp_sym_encrypt` keyed off a KMS-managed secret, or move to object storage with server-side encryption and store only the key. v1 is acceptable as long as the docker volume isn't shared.

## Sign-off

**pass** — zero high-severity findings. Three medium findings (xlsx zip-bomb unboundedness, CORS `*`, `0.0.0.0` bind) are all v1-deploy footguns rather than confidentiality/integrity breaches in the spec'd single-user-localhost trust model, and all three are concrete `path:line` items with one-paragraph fixes. Nine low findings round out a real defense-in-depth backlog: silent DSN fallback, weak example creds, JSON decode → 500, missing body-size caps on JSON endpoints, missing security headers, no rate limit, ILIKE wildcard amplification, dropped rollback errors, silent graph overwrite, and BYTEA at-rest encryption as a v2 item. All carry into `retro.md > Security findings (carry-over)`.

**Anti-bias note**: the verdict is `pass` and that is correct — the spec is explicit that v1 ships without auth and is deployed on localhost-only, which moves the entire authn/authz/CORS/bind cluster out of "exploitable in v1" and into "v2 prerequisite." The medium findings are not whitewashed: they are real and they will become blocking the moment this binary is deployed to anything reachable beyond the developer's loopback. Engineer + lead should flag the three mediums to the user before any non-loopback deploy.
