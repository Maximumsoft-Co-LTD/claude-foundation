# Security review: Homebrew tap formula for claude-foundation

**Plan**: [./plan.md](./plan.md)
**Reviewed**: 2026-06-11
**Trigger**: exec (shell exec / argv handling in the generated `bin` wrapper) + path (install.sh copies source → target via the wrapper) — single bucket-group, no fanout
**Verdict**: pass

## Threat model (one paragraph)
The new attack surface is a generated `bin/claude-foundation` wrapper that an end user runs by hand, plus the `install.sh` it execs (unchanged by this run, but now reachable through the brew path). The trust boundary is the user's own shell: whoever runs `claude-foundation` already has the privileges of that shell, so the relevant threats are not privilege escalation but (a) a caller's argv breaking out of `argv` into shell execution, (b) a caller redirecting the source tree so the installer copies attacker-controlled files into the project (the cycle-1 fix targets exactly this), (c) writes escaping the intended target directory via path traversal / symlink / `expand_path` abuse, and (d) the jq merge corrupting or clobbering a user's existing `settings.json`. The build-time values `#{libexec}` and `#{bin}` are Homebrew-interpolated from the Cellar prefix, not from user input, so they are trustable. A separate, documented supply-chain concern is that the HEAD-only formula clones a moving `main` over HTTPS with no `sha256` pin.

## Checklist

- [x] **Input** — `Formula/claude-foundation.rb:13` wrapper is `exec "#{libexec}/install.sh" "$@" --source "#{libexec}"`. `exec` with an argv list does **no** shell re-parsing of `"$@"`; quoting is correct (`"$@"`, not `$@` or `$*`), so a target path containing spaces, `;`, `$(...)`, backticks, or newlines is passed as a single literal argv element — no breakout into shell execution. The interpolated `#{libexec}` is a Homebrew build-time path, not caller input. ✓
- [x] **Authn / authz** — N/A. No endpoints, sessions, tokens, or trust elevation; the tool runs entirely with the invoking user's existing shell privileges. ✓ (N/A)
- [x] **Secrets / crypto** — no secrets, keys, or test credentials in the formula or README diff; no crypto introduced. The `protect-secrets.sh` hook that ships in the payload is copied verbatim, not invoked here. ✓
- [x] **Output** — install.sh prints colorised plan/status lines (`install.sh:22-25`); no untrusted text is reflected into a shell-interpreted context, and errors via `fail()` print a path string but no stack trace or secret. ✓
- [x] **Infra-adjacent** — file writes go through `cp "$src" "$dst"` with `mkdir -p "$(dirname "$dst")"` (`install.sh:373-374`), where `$dst` derives from `$TARGET_PATH/$rel` and `$rel` is a fixed allow-list of foundation-owned relative paths (`install.sh:178-198`), not caller-supplied. The trailing-`--source` last-wins fix and the self-copy guard are the load-bearing controls — assessed per-bucket below. No new outbound network call is added by this run; the only network action is `brew`'s own git clone over HTTPS (see supply-chain finding). ✓

### Per-bucket assessment

**Bucket 1 — shell exec / argument injection.** Closed. The wrapper uses `exec` with an argv list (`"$@"`), so the shell never re-evaluates caller arguments; there is no `eval`, no `sh -c "...$@..."`, no unquoted expansion. The cycle-1 fix — appending `--source "#{libexec}"` *after* `"$@"` — holds: `install.sh`'s parser (`install.sh:100-102`) assigns `SOURCE_PATH="$2"` on *every* `--source` it sees and the loop runs to completion over all of `"$@"` before any path resolution (the only early exits are `--help`→exit 0 and `fail()` on a malformed flag), so the wrapper's trailing `--source` is parsed last and is the last-occurrence winner. A caller passing their own `--source /evil` in `"$@"` is overridden by the trailing libexec path. Verified by re-reading the parser, not by trusting the AC. `#{libexec}` is build-time-trusted. No finding.

**Bucket 2 — path handling / arbitrary file write.** No exploitable write-escape via the brew path. Source is pinned to `libexec` (bucket 1), so the *copied content* is trusted; the only caller-controlled value is `[target-path]`. `expand_path` (`install.sh:114-129`) resolves `~` and canonicalises an existing dir via `cd && pwd`; for a non-existent leaf it canonicalises the parent and appends the literal basename. The destination paths are `$TARGET_PATH/$rel` where `$rel` is a hardcoded allow-list (`install.sh:178-198`), so a caller cannot inject a `../` into `$rel` to climb out of the target. `cp` follows a symlink at `$dst` if the user pre-planted one, but that requires the caller to have already written into their own chosen target — no privilege boundary is crossed (it is the user's own tree). The self-copy guard (`install.sh:166-168`) compares the resolved `$TARGET_PATH` against `$SOURCE_PATH` and `$SOURCE_PATH/*` and `fail`s on overlap; with source = libexec (a read-only Cellar path distinct from any user project) the guard holds and also prevents clobbering the packaged source. No finding. (Minor robustness note: the guard is a prefix-string match on canonicalised paths, not symlink-resolved on both sides — see low finding.)

**Bucket 3 — supply chain.** Real but documented and accepted. `Formula/claude-foundation.rb:4` is HEAD-only (`head "...git", branch: "main"`) with no `url`/`sha256`. `brew install --HEAD` git-clones the live `main` over HTTPS. HTTPS + git transport mitigate passive MITM, but there is **no content pinning**: a compromised upstream account, a malicious merge to `main`, or a branch force-push ships arbitrary code (the payload is executable shell + agent definitions) to every installer at their next `brew install --HEAD` / `brew upgrade`. Severity: medium (requires upstream compromise to exploit; affects all HEAD installers; the payload is code). This is the spec's documented future-hardening path (`spec.md:39,55` → Out-of-scope: cut a tagged release, add `url` + `sha256`). Non-blocking carry-over.

**Bucket 4 — settings.json jq merge.** Confirmed safe as described. The merge (`install.sh:406-461`) runs only when the target already has a `settings.json` AND a foundation hook is unwired (`install.sh:330,341-344`). It: writes a timestamped backup first (`install.sh:407-409`); builds the merged document in a variable via a `jq` filter that is idempotent (each hook upserted only if no entry with the same `.command` exists — `install.sh:428-431`) and preserves all other user keys (permissions/model/env/their hooks); validates the result parses as JSON (`printf '%s' "$merged" | jq empty` — `install.sh:448`) *before* overwriting; and on any failure restores from the backup and falls back to dropping a non-destructive snippet (`install.sh:452-460`). The `--slurpfile`/`jq` inputs are the foundation's own source `settings.json` and the user's file as data, never string-concatenated into a shell or query — no injection vector. No finding.

## Findings

### Blocking (severity = high)
- None.

### Non-blocking (severity = medium / low)
- `Formula/claude-foundation.rb:4` — **(medium)** HEAD-only formula tracks a moving `main` over HTTPS with no `sha256`/`url` pin; a compromised upstream or `main` force-push ships arbitrary executable payload to all `--HEAD` installers. → Accepted, documented decision: cut a tagged release and add `url` + `sha256` (and ideally enable branch protection / require-signed-commits on `main` in the interim). Already tracked in `spec.md:39` (Out-of-scope) and README's "Future hardening" note. Carry into `retro.md` as the standing hardening item.
- `install.sh:166-168` — **(low)** the self-copy guard is a canonicalised-path prefix string match, not a symlink-resolved comparison on both operands. Via the brew path this is inert (source = a distinct read-only Cellar `libexec`, target = a user project), so it does not affect this run; noting only because the wrapper now makes `install.sh` a more widely-invoked entry point. → No change required for this run; carry-over as a defensive note if `install.sh` is ever revisited (per spec, install.sh's core logic is not modified here).
