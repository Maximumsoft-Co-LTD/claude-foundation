เทียบกับ spec-workflow ตัวอื่น (spec-kit, agent-os, ฯลฯ)

  • Type-aware + size-aware ไม่ใช่ one-size-fits-all — fix/refactor/spike/docs เดินคนละเส้น, งาน XS มี patch lane ที่ spawn เดียวจบ ส่วนใหญ่ในตลาดบังคับ machinery เต็มกับทุกงาน
  • Enforcement เป็นโค้ด ไม่ใช่ความหวัง — ตัวอื่นเกือบทั้งหมดเป็น prompt ล้วน ของเรามี PreToolUse/PostToolUse hooks 4 ตัว + เทสต์ 68 assertions ครอบตัว hooks เอง
  • เศรษฐศาสตร์ model tier ในตัว — haiku/sonnet/opus ปักราย role มี guard กันเผลอรันแพง + นโยบายรวมที่ model-tiers.md — จ่าย opus เฉพาะจุดที่คุ้ม
  • Skill เป็น on-demand references — always-on layer บางมาก (~1.3k คำ) ความรู้ 26 skills โหลดเฉพาะตอน trigger และหลัง v2.8.1 โหลดครั้งละ ~⅓ ของเดิม
  • ยอมรับ trade-off เป็นลายลักษณ์อักษร — ทุก shortcut ที่แลก correctness ถูกบันทึกและมี backstop (spot-check, near-miss peek) ไม่ใช่ magic ที่พังเงียบ

จุดอ่อนของเรา (พูดตรงๆ)

  • Overhead ต่อ run สูงกว่า vanilla — run M/L เต็มรูปกิน token และเวลามากกว่าถามตรงๆ หลายเท่า — คุ้มเมื่องานมี blast radius จริง ไม่คุ้มกับ quick hack (ซึ่งไม่ควรเข้า /dev ตั้งแต่แรก)
  • State machine ฝั่ง prompt ยังไม่มี regression test — hooks มีเทสต์แล้ว แต่ orchestrator flow ทั้งเส้นพิสูจน์ด้วยการใช้จริง golden-run smoke test อยู่ในแผน v2.9
  • Multi-repo เขียนได้ทีละ repo — อ่าน/รีวิว/ตรวจข้าม repo ขนานได้ แต่ implement/ship ปักที่ repo หลัก by design — finding ข้าม repo ต้องให้คนตัดสิน
  • ผูกกับ Claude Code รุ่นใหม่ — direct nesting ต้อง v2.1.172+ และ convention ทั้งชุดมี learning curve ก่อนอ่าน run แรกออก
  • คุณภาพ spec ขึ้นกับคำตอบ interview — ระบบ grill ให้ แต่ตอบมั่วก็ได้ spec มั่วแบบมีพิธีการ
  • team-* reviewers ตัดขาดจาก upstream แล้ว — ได้ความสอดคล้องกับไปป์ไลน์ แลกกับไม่ได้ของใหม่จาก pr-review-toolkit อัตโนมัติ

🛡️ แก้ bug จริงใน hooks v2.6.9

สอง fail-open ที่ซ่อนอยู่ในกลไกป้องกัน state — เจอจากการ audit ทั้งระบบ

  • Guard Case 4 fail-closed — เดิมถ้าอ่าน model: pin ของ worker ไม่ได้ hook จะ crash แล้วปล่อยผ่านเงียบๆ ตอนนี้ปฏิเสธพร้อมเหตุผลชัดเจน
  • เอกสารตรงกับความจริง — caveat เรื่อง guard fail-open เมื่อมี run ขนาน, fast-path ที่รวม test-plan, แกน surface-fanout ใน WORKFLOW.md

⚡ โปรไฟล์ Opus 4.8 + Model tiers v2.7.0

ปิดช่องว่าง self-verification ด้วย external feedback — จุดที่ benchmark บอกว่า 4.8 ≈ รุ่นที่สูงกว่าเมื่อ harness ป้อนผลตรวจกลับให้

  • artifact-lint.sh --hook — ทุกครั้งที่เขียน artifact ใน .workflow/ จะโดน lint ทันทีแบบ warn-only (ไม่ block) — placeholder ค้าง, section หาย เจอตั้งแต่ตอนร่าง
  • lint.sh typecheck — ไฟล์ .ts/.tsx เช็คด้วย tsc จาก tsconfig ใกล้สุด (กรองเฉพาะไฟล์ที่แก้), .py ด้วย pyright — feedback ผิดพลาดทันทีหลังทุก edit
  • แก้กับดัก recall — team-code-reviewer เลิก pre-filter "confidence ≥ 80" (โมเดลเชื่อฟังคำสั่งห้ามจุกจิกจน finding จริงหาย) — รายงานหมดแล้วให้ lead กรองตอน synthesis ที่มี context ครบ
  • Review fanout default-ON ที่ M/L — จะปิดต้องมีเหตุผล ไม่ใช่ค่าเริ่มต้น
  • model-tiers.md — นโยบาย tier ทั้งหมดในไฟล์เดียว + floor ของ built-in agents ปรับได้ผ่าน env
  • Fork ประกาศ DETACHED — team-* reviewers วิวัฒน์ตามไปป์ไลน์นี้ ไม่ตาม upstream อีกต่อไป

⚖️ คืน correctness ที่เคยแลกไป v2.7.1
