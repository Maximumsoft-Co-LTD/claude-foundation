# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This repo packages an opinionated **command workflow for Claude Code, aimed at AI engineers** — reusable slash commands, sub-agents, hooks, skills, and the `/dev` pipeline — so other repos can adopt them. The audience is engineers using Claude Code as their primary development surface; the artifacts here are the product, not an application.

Key surface area:
- `.claude/orchestrator.md` — the main-agent playbook for the `/dev` workflow. There is **no** `orchestrator` sub-agent; the main agent IS the orchestrator (a sub-agent can't call `AskUserQuestion` to run the interview; the splittable workers do hold `Agent` and self-dispatch their own helpers via direct nesting, but the interview, the gate, and the single-writer `state.json` stay with the orchestrator). Never call `Agent(subagent_type="orchestrator")`.
- `.claude/agents/` — `/dev` workers (`pm`, `lead`, `engineer`, `qa`, `retro`), the team-mode `uxui` designer (spawned only by `/uxui-plan`, not by the `/dev` orchestrator), and parallel `team-*` fanout workers, each with an explicit `model:` set for cost/speed tuning.
- `.claude/commands/` — slash commands: `dev.md` (the full `/dev` pipeline) plus the **team-mode** commands that each drive one slice into a shared `.workflow/<id>/` run — `spec.md` (`pm` → spec), `dev-plan.md` (`lead` → plan), `test-plan.md` (`qa` → test-plan), `uxui-plan.md` (`uxui` → UX plan), and `implement.md` (gate-if-needed + autonomous Phase 2). The command's main agent plays the orchestrator (interview/gate + single-writer `state.json`); the named worker does the file work. `/implement` runs the same gate + Phase 2 as `/dev --resume` (interchangeable); `/uxui-plan` is **not** a `/dev` state-machine step (it leaves the resume cursor untouched). Installers ship the whole `.claude/commands/` dir, so new commands need no manifest edit.
- `.claude/rules/` — always-on "by default" rules. These are load-bearing: the fundamentals get applied via this always-on context, not via the Skill tool (project skills don't auto-trigger). The working agreements below point here.
- `.claude/skills/` — the fundamentals skills (full detail loaded on demand: the construction chain `ddd-strategic` → `programming-fundamentals` → `concurrency-fundamentals` → `database-fundamentals` → `hexagonal-backend` → `api-design-fundamentals` → `architecture-fundamentals` → `queue-fundamentals` → `security-fundamentals` → `observability-fundamentals`, the process/verification skills `coding-discipline` / `debug-fundamentals` / `refactoring-fundamentals` / `testing-fundamentals`, and the delivery channel `git-workflow` / `delivery-engineering`) plus product skills (`brainstorming`, `plan-writing`, `qa-handoff-note`, `fanout-team-agents`, frontend/UX, `skill-creator`).
- `.claude/hooks/` — `dev-agent-guard.sh` (PreToolUse spawn guard for the `/dev` state machine), `dev-state-mark.sh` (PostToolUse state marker), `lint.sh` (PostToolUse linter dispatch), `protect-secrets.sh` (PreToolUse guard that blocks `Read`/`Grep`/`Bash` from reading `.env` and credential files; allow-lists `*.example`/`*.template`/`*.pub`). `no-direct-main-commit.sh` is an **opt-in** PreToolUse `Bash` guard (shipped but **not wired by default**) that blocks a `git commit` while on `main`/`master` — branch-first; fails open on detached HEAD / non-repo, honours `ALLOW_MAIN_COMMIT=1`, ships a `--self-test`. Register it under `PreToolUse`/`Bash` in `.claude/settings.json` to activate.
- `WORKFLOW.md` + `.workflow/` — the type-aware phase matrix, run templates, and per-run `state.json` / artifacts that drive `/dev --resume`. The matrix is gated by three axes: `Type` (which phases), `size` (how much machinery), and `field` (**greenfield | brownfield** — the formalised "new vs existing code" call recorded in `state.json`). Brownfield gates the **understand → lock → change → improve** discipline: a `Current state` map (understand), a characterization baseline before the change (lock), and the bounded **improve** phase 7½ (`engineer` Mode D — behaviour-preserving cleanup of the touched code, brownfield `feat`/`fix` only); greenfield skips all three. Canonical `field` definition lives in `plan-writing > references/size-tiering.md > Greenfield vs brownfield`; it ratchets greenfield → brownfield one-way via a `FIELD_UPGRADE` signal.

## Working agreements (carried from user-level config)

The fundamentals are applied via the always-on rules in `.claude/rules/` (project skills don't auto-trigger). **Each rule names its own trigger and points at the full skill body at `.claude/skills/<skill-name>/SKILL.md`** — the rules are the detection layer; do not restate their trigger lists here. Load the skill body on demand for the why/how, skip lists, and worked examples, and invoke it *before* the first line of the work it governs. **The canonical cross-skill run order lives in `.claude/rules/fundamentals.md`** (always-on and shipped to adopting repos by the installers) — rules and skills point there instead of restating the chain.

- **LSP first** — when an LSP tool is available, use it for diagnostics, go-to-definition, and references before grep/read. (From `~/.claude/CLAUDE.md`.)
- **`coding-discipline` wraps every code task** and runs first as the conduct check (assumptions stated → minimum non-speculative code → surgical diff → verifiable definition of done); it routes to the construction/debug/refactor skills per their rules and must not re-teach them.
- **Ignore the OpenWolf parent directive** — the parent `/Users/hashtagf/Desktop/Work/CLAUDE.md` tells every session to read `.wolf/OPENWOLF.md` / `.wolf/cerebrum.md` / `.wolf/anatomy.md`. No `.wolf/` tree exists in this project — do not act on those instructions here.
