## ผลเปรียบเทียบ

| ผล | v3.6.0 | v3.6.1 | v3.6.2 |
|---|---:|---:|---:|
| ส่งมอบ, archived, oracle และ clean install ผ่าน | 9/10 | 9/10 | 9/10 |
| คุณภาพโค้ดที่วัดได้ผ่าน | 9/10 | 9/10 | 9/10 |
| เวลา host รวม 9 คู่ที่สำเร็จ | 842.3 วินาที | 747.4 วินาที | 847.9 วินาที |

เทียบกับ v3.6.0: v3.6.1 ใช้เวลา host ลดลง 11.3% แต่ค่าใช้จ่ายเพิ่ม 1.8%;
v3.6.2 ใช้เวลาเพิ่ม 0.7% และค่าใช้จ่ายเพิ่ม 5.3% เมื่อเทียบ v3.6.2 กับ v3.6.1
เวลาเพิ่ม 13.5% และค่าใช้จ่ายเพิ่ม 4.0% ใน 9 คู่ที่วัดค่าครบ จำนวนคู่ด้านต้นทุน
ต่างกันเพราะ Python API ของ v3.6.0 ไม่มี cost envelope จึงรายงานไม่ทราบและไม่เอามาคิด

เวลาเป็น host stopwatch รวม session ซ่อม สำหรับ run สำเร็จวัดถึง `proven`
ไม่รวม backend oracle, Land และ clean install ภายหลัง เวลา `labElapsedMs`
ของงานทั้งรอบยังอยู่ในข้อมูลดิบ ไม่เอา run ที่ล้มเหลวมานับเป็นความเร็วที่ดีขึ้น

## ข้อที่ต้องติดตามใน candidate ถัดไป

Project Tracker ทั้งสามรุ่นผ่าน 32/33 แต่ตก `CASE_TESTS_EXIST` โดย oracle ต้องมี
อย่างน้อย 15 tests ที่ผ่าน และ tests ต้องจับข้อบกพร่องใน seed เดิมได้ v3.6.2
รายงาน 10 tests รอบซ่อมของแต่ละรุ่นเรียก Build/Prove แต่ไม่แก้งานเพราะ harness
ไม่คืน repair plan จึงยังตก hidden oracle, ไม่ Land และไม่ได้ตรวจ clean install

การซ่อมตาม oracle ภายนอกและความเพียงพอของ tests ยังเป็น finding ที่ไม่ปิด
ต้องเก็บไว้ตรวจ candidate ใหม่ ไม่ลดเกณฑ์ oracle และไม่ถือ `proven` เป็นส่งมอบสำเร็จ
การทดลองนี้ยังแยกไม่ได้ว่าเกิดจาก regression ของ skill ใหม่โดยตรง

ค่าใช้จ่ายที่ทราบรวม **อย่างน้อย $13.3974738** ไม่ใช่บิลครบ เพราะ Python API ของ
v3.6.0 ไม่มี cost result หากกันงบเต็ม $2 สำหรับ run นั้น ยอดสูงสุดที่กันไว้คือ
$15.3974738 ซึ่งอยู่ในงบที่อนุมัติ $40
ตัวเลขนี้รวม cost result ของ CLI host หลักและงบของ host ไม่ได้วัดค่าใช้จ่าย
provider/reviewer ที่อาจเรียกเก็บแยก จึงไม่ใช่ยอดใบแจ้งหนี้ของบัญชี
